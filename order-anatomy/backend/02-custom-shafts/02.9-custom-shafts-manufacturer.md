# Giving an order to a producer (`manufacturer_order`)

FeetF1rst does not make every shaft itself. The admin can give an order to an outside producer (a factory). The e-mails to producers are in Italian. This file covers the producer accounts, how an order is given to one, and what the producer sees.

The tables are in `prisma/manufacturer.schma.prisma`. The code is in `module/v3/manufacturer/`. Every address starts with `/v3/manufacturer`.

## The story, in order

1. The admin creates a producer account in the admin dashboard (name, address, phone, e-mail, password).
2. For an order, the admin makes and uploads the producer sheet (see `02.7-custom-shafts-invoices-and-emails.md`).
3. In the order list or order detail, the admin clicks "An Produktion" and picks a producer (`AssignManufacturerModal.jsx`).
4. The order gets a production number if it has none, and the producer gets an Italian e-mail with the sheet, the 3D files, and a link that logs them in.
5. The producer opens the link and lands on the producer area of the Partner Dashboard app (`/ubersicht/bestellungen`). They see their orders and some counts.
6. The admin sees in the order detail which producer has the order, and can take it back.

The producer cannot report progress from any screen yet (see "What the producer cannot do").

## What is stored

### Producer (`manufacturer`)

| Column | Meaning |
| --- | --- |
| `name`, `address`, `phone` | Contact data |
| `email` | Login name, unique |
| `password` | Stored as plain text. Empty when the admin left it out. |
| `role` | `MANUFACTURER` |

A producer is not a `users` row. It has its own table and its own login.

### Order given to a producer (`manufacturer_order`)

| Column | Meaning |
| --- | --- |
| `custom_shafts_id` | The order. Deleted together with the order. |
| `manufacturer_id` | The producer. Deleted together with the producer. |
| `status` | The producer's progress: `order_received` (default), `waiting_for_last`, `in_progress`, `in_production`, `completed`, `issue_question`, `delivered`, `cancelled` |

This status is separate from the order's own status. Nothing copies one into the other.

### Other tables

| Table | What it holds | Used |
| --- | --- | --- |
| `manufacturer_order_notes` | Notes on a producer order, written by producer or admin | No code reads or writes it |
| `manufacturer_settings` | One default producer per category (unique per category) | Saved and shown in the admin's settings window. Nothing uses it to pick a producer. |
| `manufacturer_outstanding` | Amounts owed: name, producer text, short description, payable and paid amount, a shop link | Admin list with create, edit, delete. Not linked to producers or orders. |

## Addresses

| Method and path | Logins | What it does |
| --- | --- | --- |
| `POST /create`, `PATCH /update/:id`, `DELETE /delete/:id` | Admin | Producer accounts |
| `GET /get-all`, `GET /get-all-lite`, `GET /get-by-id/:id` | Admin | Read producers. `get-all` also returns the password. |
| `POST /order/assign` | Admin | Give an order to a producer |
| `POST /order/remove` | Admin | Take one or more orders back |
| `GET /order/get-all` | Producer, admin | A producer's orders |
| `GET /order/by-shaft/:customShaftsId` | Producer, admin | Which producer has this order |
| `GET /order/get-by-id/:id` | **No login** | One producer order with the order, customer, and producer |
| `PATCH /order/update-status` | **No login** | Change the producer status of many producer orders |
| `POST /settings/set`, `GET /settings/get-all` | Admin | Default producer per category |
| `/outstanding/create`, `get-all`, `get-by-id/:id`, `update/:id`, `delete-bulk` | Admin | Amounts owed |
| `POST /auth/login` | No login | Producer login |
| `GET /auth/profile`, `PATCH /auth/update-profile`, `PATCH /auth/change-password` | Producer | Own account. Profile returns the password. |
| `POST /auth/forgotpassword/sendotp`, `verifyotp`, `reset`, `recentotp` | No login | Forgotten password |
| `GET /calculation/get-calculation-data` | Producer | Counts on the producer's start page |

Callers: the admin dashboard (`apis/ManufacturerApis/getAllManufacturer.js`, `manufacturerOutstandingApis.js`) and the producer area (`apis/manufacturer/bestellubersichtApis.ts`, `profileApis.ts`). No screen calls `order/update-status`, `order/get-by-id`, `auth/login`, or the forgotten-password addresses. The producer logs in only through the e-mail link.

## Giving an order (`assignOrder`)

Body: `orderId` (the order) and `manufacturerId`.

| Check | Answer |
| --- | --- |
| A value missing | `400` |
| Order or producer unknown | `404` |
| Order already `Versandt` or `Ausgeführt` | `400` |
| Order already given to a producer | `400` |
| No producer sheet uploaded | `400` |

Then, in one transaction:

1. **Production number.** The order keeps its `production_number` if it has one. Otherwise it gets the highest number among orders already given to a producer + 1, starting at `100`, and that number is saved on the order.
2. **Producer order.** A `manufacturer_order` row with status `order_received`.

After that, a login link is made for the producer (it does not expire) and the e-mail "FeetF1rst – Nuovo ordine assegnato …" is sent with the sheet, the 3D files, and the link to `/ubersicht/bestellungen`. The answer does not wait for the e-mail.

The order's own status is not changed.

## Taking it back (`removeOrderFromManufacturer`)

Body: `manufacturerId` and `orderId` (one or a list). Deletes the producer orders. `404` when none was deleted. The production number stays on the order.

## What the producer sees

`GET /order/get-all` lists the producer's orders, newest first: filters `status` and `catagoary` (comma-separated), `search` (order number, customer name and e-mail, other customer name, model name), `limit` (1–100, default 20), `cursor`. Each row has the order with files, the producer sheet, and the product name and picture.

`GET /calculation/get-calculation-data` counts the producer's orders: total, in production (`waiting_for_last`, `in_progress`, `in_production`), question or problem (`issue_question`), urgent, and due within 3 days.

## What the producer cannot do

| Wanted | Today |
| --- | --- |
| Report progress | No screen sends `order/update-status`. The status stays `order_received` unless someone calls the address directly. |
| Open one order | The detail page shows fixed sample data (`getBestellungDetailStatic`), not the real order |
| See the next page of orders | The server sends `pagination.nextCursor`; the screen reads `pagination.cursor`, so the next page never loads |
| See the customer name | The server sends `vorname` and `nachname`; the screen reads `firstName`, `lastName`, `name`. Only the "other customer name" or "-" appears. |
| See their own status | The table shows the order's status (`custom_shafts.status`) and falls back to the producer status only when that is empty, which it never is. The "needs attention" filter therefore never finds an `issue_question` order. |

This is problem 22 in `02.5-custom-shafts-problems.md`. The account weaknesses are problem 21.

## A worked example

Shaft `10023` has its producer sheet uploaded. It got a production number at create (the shop's prefix + `023`, see `02.1`).

1. The admin clicks "An Produktion" and picks producer "Rossi" (`m1`). The screen sends `POST /v3/manufacturer/order/assign` with `orderId` = id of `10023`, `manufacturerId` = `m1`.
2. The database now has a `manufacturer_order` row (order `10023`, producer `m1`, status `order_received`). `10023` keeps its production number. (An order without one would get the next number from `100` upward.)
3. Rossi gets "FeetF1rst – Nuovo ordine assegnato …" with the sheet and a link to `/ubersicht/bestellungen?token=…`.
4. Rossi opens the link. The order appears in the list with its production number. The customer column shows "-" (the customer has a record, but the screen reads the wrong fields).
5. In the admin's order detail, `GET /order/by-shaft/<id of 10023>` shows Rossi as the producer.
