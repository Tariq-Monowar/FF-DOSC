# Ordering a shaft or a complete shoe

This file covers the two main orders: a shaft (`Massschafterstellung`) and a complete shoe (`Komplettfertigung`). Both are created by `POST /custom_shafts/create`. The same address also exists as `/v1/custom_shafts/create`.

The handler is `createTustomShafts` in `module/v1/admin_order/custom_shafts.controllers.ts`. Logins allowed: partner, employee, admin. Only the partner dashboard calls it.

## The story on the partner's screen

1. The partner opens the catalogue (`dashboard/custom-shafts`) and picks a model. They land on `custom-shafts/details/[id]`, where `[id]` is the catalogue shoe.
   If they upload their own shoe picture instead, they work on `custom-shafts/product-order/[id]`. That is a "custom model" order.
2. The page fills the category, closure, zipper, name, price, and photo from the catalogue. If the partner chooses "Ausführung wie im Katalog", the leather, lining, seam, and the catalogue's leather picture are filled too. All of this happens in the browser.
3. The partner picks the customer, uploads the two 3D last files if they have them, chooses how the lasts reach FeetF1rst, and reviews the PDF of the order.
4. A confirmation box offers three choices:

| Button | What happens |
| --- | --- |
| Weiter ohne Boden | The shaft order is sent now (`Massschafterstellung`) |
| Boden konfigurieren | The partner goes on to the sole screen (`Details/Bodenkonstruktion.tsx`). When they finish, one order with both shaft and sole is sent (`Komplettfertigung`). |
| Entwurf speichern | The order is saved as a draft (`?is_draft=yes`) |

5. A sent order appears in "Aktivität" on `balance-dashboard`. The partner receives a confirmation e-mail, and the admins get a notification.

The browser builds the order with `prepareCollectionFormData` (catalogue order) or `prepareStep1FormData` (custom model, in `utils/customShoeOrderHelpers.ts`). The request address is built by `buildCustomShaftsCreateUrl` in `lib/customShaftsPriceQuery.ts` and sent by `createMassschuheWithoutOrderIdWithoutCustomModels` or `createMassschuheWithoutOrderId` in `apis/MassschuheAddedApis.ts`.

## What the request carries

The body is a form with files.

### Files

Each can be a file, or a web address of a file already uploaded. The partner screen uploads large files in the background first, then sends their addresses, so the order is saved quickly.

| Field | What it is |
| --- | --- |
| `image3d_1`, `image3d_2` | Right and left last, 3D |
| `invoice` | The PDF the partner reviewed |
| `invoice2` | Second invoice |
| `paintImage` | Painted leather areas. With "Ausführung wie im Katalog" this is the catalogue's own leather picture address. |
| `zipper_image` | Zipper position |
| `ledertyp_image` | Leather layout |
| `custom_models_image` | The partner's own shoe picture (custom model only). Saved on the `custom_models` row, not on the order. |
| `staticImage`, `threeDFile` | Sole picture and sole 3D file, complete shoe |

When a file is given as a web address, the order saves that address as it is. It does not make a copy.

### Main fields

| Field | What it is |
| --- | --- |
| `customerId` or `other_customer_name` | The customer. One is required unless it is a draft. |
| `other_customer_number` | Customer number when there is no customer record |
| `mabschaftKollektionId` | The catalogue shoe. Required for a catalogue order unless it is a draft. |
| `custom_models_name`, `custom_models_price`, `custom_models_verschlussart`, `custom_models_gender`, `custom_models_description` | The partner's own model. Closure, price, and picture are required once any of these is sent. |
| `Massschafterstellung_json1` | The shaft specification |
| `Massschafterstellung_json2` | The sole specification. Present only for a complete shoe. |
| `catagoary` (or `custom_shafts_catagoary`) | `Massschafterstellung` or `Komplettfertigung`. When missing, both specifications mean complete shoe, one means shaft. |
| `totalPrice` | The price the screen calculated |
| `versenden` | Sending details |
| `deliveryDate`, `delivery_length` | Only used when the server does not calculate them itself |
| `sample_sending_date` | When the partner will post the lasts |
| `lest_sending_type` | `feetf1rst_shipping` or `self_shipping`. `grouped` is read as `feetf1rst_shipping`, `my_self` as `self_shipping`. |
| `shipping_type1`, `shipping_cost1`, `shipping_type2`, `shipping_cost2` | Shipping both ways |
| `postalCode`, `street`, `city`, `state`, `country`, `delivery_info` | Pickup address. The country must be a European code from `EUROPE_COUNTRY_CODES`. |
| `shoe_order_id` | The partner's shoe order this belongs to |
| `feedback_id` / `custom_shafts_feedback_id`, `sample_id` / `custom_shafts_id` | The fitting feedback and the test shoe this order follows. Each pair must be the same value. |
| `clinica_assistant_order_components_id` | The care-plan component that sent the order |
| `is_last` | `true` means the 3D files are finished lasts |

### Query values

| Value | What it does |
| --- | --- |
| `is_draft=yes` | Save as a draft |
| `prise=neutral` | Save as `neutral` without being a draft |
| `withgroup=true` | Do not put the order in a same-day group |
| `shifting_bundle=yes` / `no` | When `lest_sending_type` is missing: `yes` means FeetF1rst collects, `no` means the partner sends |
| `shipping_id` | Join this existing pickup shipment |
| `shipping_order_id` | Comma-separated orders to ship together with this one. Not together with `shipping_id`. |
| `createLabel=yes` | Make the FedEx pickup label now. Needs `shipping_id` or `shipping_order_id`. |

The partner screen also sends `custom_models` and `isCourierContact` in the address. The server does not read either. It decides "custom model" from the `custom_models_*` fields, and it does not use courier contacts here. It also reads `deleveary_method` but does nothing with it.

## What the server checks, in order

| Situation | Answer |
| --- | --- |
| Country is outside Europe (not a draft, not joining a group) | `400` "Invalid country code" |
| Some custom-model fields are sent, but closure, price, or picture is missing | `400` "Missing required custom model field(s): …" |
| No customer and no customer name (not a draft) | `400` "Either customerId or other_customer_name is required" |
| `lest_sending_type` has another value | `400` |
| Feedback and sample ids disagree, or the sample is not the feedback's test shoe | `400` |
| Feedback or test shoe does not exist | `404` |
| The login's user no longer exists | `401` "User not found. Please log in again." |
| Customer does not exist | `404` "Customer not found" |
| Catalogue order without `mabschaftKollektionId` (not a draft) | `400` "Missing shoe model: send mabschaftKollektionId (catalog)" |
| Catalogue shoe does not exist | `404` "Maßschaft Kollektion not found" |
| `shoe_order_id` does not exist | `404` "shoe_order_id not found" |
| Both `shipping_id` and `shipping_order_id` | `400` |
| `createLabel=yes` without a group | `400` |
| The group or the listed orders are not this partner's | The error from the shipping check |
| A label is wanted without 3D files, and the address is incomplete | `400` "Missing required shipping address fields: …" |
| `delivery_length` is not a whole number of `0` or more | `400` |

If a check fails after files were uploaded, the server deletes those uploaded files again.

## What is saved

One `custom_shafts` row. Column by column, for a sent order:

| Column | Value |
| --- | --- |
| `partnerId` | The partner. For a partner login, the login's `id`. When the order belongs to a shoe order, that shoe order's partner. |
| `orderNumber` | Next number for that partner, starting at `10000` |
| `production_number` | Partner prefix + last 3 digits of the order number |
| `catagoary` | `Massschafterstellung` or `Komplettfertigung` |
| `status` | `lasts_received` when both 3D files are there (or `is_last` is true); otherwise `Bestellung_eingegangen` |
| `last_status` | `Angekommen` in the first case; otherwise the default `Unangekommen` |
| `order_status`, `order_type` | `active` and `normal`. A draft is `neutral` and `draft`. |
| `production_start_date` | Now, when 3D files are there; otherwise empty |
| `deliveryDate`, `delivery_length` | Calculated from the category's working days when 3D files are there; otherwise the body's values |
| `sample_sending_date` | Empty when 3D files are there; otherwise the body's date |
| `production_cost` | From the category setting |
| `totalPrice` | The body's price |
| All file columns | The addresses from above |
| `Massschafterstellung_json1`, `Massschafterstellung_json2`, `versenden`, `delivery_info` | Read from text into JSON |
| `shipping_type1/2`, `shipping_cost1/2` | From the body. A missing cost is taken from `shipping_pricing` for that type. |
| `lest_sending_type` | As described above |
| `isCustomeModels` | `true` for a custom model |
| `maßschaftKollektionId` | The catalogue shoe (catalogue order only) |
| `customerId`, `shoe_order_id`, `custom_shafts_feedback_id`, `parent_custom_shafts_id`, `clinica_assistant_order_components_id` | When given |
| `package_group_id` | The same-day group for the delivery date, unless `withgroup=true` |
| `billing_month` | By the 25th rule in `02-custom-shafts.md`. Empty for a draft. |

The server does not recalculate the price from the catalogue. It saves what the partner's screen calculated.

For a custom model, a `custom_models` row is created too: name, picture, price, closure, gender, description, the partner, the customer, and this order.

## What happens after the row is saved

These steps run one after another. They are not one database transaction, so a later step can fail after the order already exists.

1. **The partner's balance.** A billing line (`admin_order_transitions`) is created with the price, status `panding`, and `orderFor: shoes`. The partner's open amount (`partner_total_amount`) goes up by the price. If a billing line already exists for the order, nothing is added again. This is `finalizeCustomShaftOrderBilling` in `custom_shafts.background.service.ts`.
2. **The shoe order.** When the order belongs to a shoe order, the shoe order is marked as made externally (`massschafterstellung_type: extern`), and its production steps are started ("Schaft fertigen", plus "Bodenerstellen" for a complete shoe). If no shoe order was sent but a customer was, the server links an open shoe order of that partner and customer that is not yet ready for pickup and has no live shaft order.
3. **The test shoe.** When this order follows a test shoe that waits for fitting, the test shoe moves to `Leisten_wird_gefräst`.
4. **Silent last order.** When this order follows a fitting feedback and a test shoe, the server also creates a last order (`Leistenerstellung`, price `0`) under that test shoe. It sends no e-mail and no billing line for it.
5. **Shipping.** Depending on the query values, the order joins a pickup group, a new pickup shipment is made, a FedEx label is created, or the partner gets the "how to send your lasts" e-mail. See `02.4-custom-shafts-shipping.md`.
6. **E-mails and notices.** The partner gets the order confirmation. Admins get the new-order e-mail and an in-app and push notice.
7. **Files to the customer's file area.** After the answer is sent, the files of this request are copied into the customer's "Drive" in the Partner Dashboard (`scheduleMasschaftDrive`). This is the app's own file store, not Google Drive; see `02.7-custom-shafts-invoices-and-emails.md`.
8. **Saved address.** The pickup address is saved to `shipping_address` for next time.
9. **Customer history.** A line is added to the customer's history.

## The answer

A sent order answers `201` with the order: id, order number, statuses, files, prices, dates, the catalogue shoe, and the partner. When it joined or made a shipment, a `shipping` part says `linked` or `processing`, and whether a label is being made.

A draft answers `201` "Draft saved successfully". It skips the balance, shipping, e-mails, Drive, and the silent last order.

## Drafts

A draft lets the partner stop and come back. It is saved with `order_status: neutral` and `order_type: draft`. It does not appear in the order lists, has no billing month, and does not count on the balance page.

### Coming back to a draft

The partner opens the draft from "Aktivität". The order page loads it through `/massschuhe-order/admin-order/get/:id` and fills every field again, including the addresses of the 3D files, the zipper picture, and the paint picture.

### Saving the draft again

`PATCH /custom_shafts/update-admin-order-after-draft/:id`, handler `updateAdminOrderAfterDraft`, called by `updateAdminOrderAfterDraft` in `apis/customShaftsApis.ts`.

- The order must be a draft or `neutral`. Otherwise `400` "Only draft or neutral orders can be updated here".
- A partner may change only their own draft. Otherwise `403`.
- Files: for each file field that is sent, the old file is deleted from storage and the new address is saved.
- Fields: order number, customer, customer name, catalogue shoe, price, discount, shipping costs and types, the custom-model and custom-sole flags, every JSON specification, the test-shoe PDF, `delivery_length`, `deliveryDate`.
- When no date is sent, the delivery date is calculated again from the 3D files on the draft.
- The catalogue field here is spelled `maßschaftKollektionId`, with `ß`. The create call uses `mabschaftKollektionId`.

This call does not send the draft. The draft stays a draft.

### Checking a draft

`GET /v3/admin-order/manage/draft-check/:customShaftsId` lists what is still missing, using the same rules as sending.

### Sending a draft

`POST /v3/admin-order/manage/send-order-to-admin/:customShaftsId?shifting_bundle=yes|no`, handler `sendOrderToAdmin` in `module/v3/admin_order/manage/manage.controllers.ts`.

The partner's screen calls the draft save first, then this.

1. `shifting_bundle` must be `yes` (ship together with others) or `no`.
2. The order must be a draft or `neutral`.
3. For a draft, every required field is checked. For a shaft: customer, the specification, number of leathers (1–4), lining and its colour name, shaft height left and right. For a sole or complete shoe: sole, sole colour or thickness where needed, heel cap pattern, heel cap, toe cap, insole, connecting leather, construction, frame, heel shape, rolling aid, loose outsole, keep lasts in the shoe. Missing fields answer `400` "Pflichtfelder fehlen: …".
4. An order that already has a pickup label is refused.
5. A partner can send only their own order.
6. The body may change the pickup address, `shipping_type1`, `shipping_type2`, `sample_sending_date`, `production_start_date`, `delivery_length`.
7. For a draft: `draft_created_at` keeps the draft's date, `createdAt` becomes now, the production clock starts now for sample, last, and sole orders, and for shaft, complete shoe, or test shoe when 3D files or received lasts are there. The billing month is set.
8. The order becomes `active` and `normal`.
9. Billing line and balance, shipping flow, and the confirmation e-mail run as for a new order.

Answer: `200` "Order sent to admin", with the saved shipping and date fields.

## A worked example

The shop "Orthopädie Weber" (partner `p1`) orders a catalogue shaft for its customer Anna Schmidt (`c1`) on Monday, 5 October 2026. The shop already has orders up to number `10022`. Its open amount on the balance page is 1,000. The admin has set 10 working days for shafts in `custom_shafts_delivery_dates`, and there is no holiday in the next weeks.

1. On `custom-shafts/details/k1` the partner picks the model, chooses the leather, uploads both 3D last files, and clicks "Weiter ohne Boden". The screen has already uploaded the 3D files and sends their addresses.
2. The request:

```text
POST /custom_shafts/create
form fields:
  customerId           = c1
  mabschaftKollektionId = k1
  catagoary            = Massschafterstellung
  totalPrice           = 289
  image3d_1            = https://…/right.stl
  image3d_2            = https://…/left.stl
  Massschafterstellung_json1 = { …shaft specification… }
```

3. The checks pass: the customer and the catalogue shoe exist. No country is sent, so the country check is skipped. No pickup address and no shipping fields are sent, so no partner→FeetF1rst shipment is made; nothing has to travel because the lasts are digital.
4. The server counts 10 working days from 5 October, skipping the weekends: the last one is Monday, 19 October.
5. The new `custom_shafts` row:

| Column | Value |
| --- | --- |
| `orderNumber` | `10023` |
| `catagoary` | `Massschafterstellung` |
| `status`, `last_status` | `lasts_received`, `Angekommen` (both 3D files are there) |
| `order_status`, `order_type` | `active`, `normal` |
| `production_start_date` | 5 October 2026, the time of the request |
| `deliveryDate` | 19 October 2026 |
| `delivery_length` | `14` (calendar days from 5 to 19 October) |
| `billing_month` | 1 October 2026 (5 October + 14 days = 19 October, before the 25th) |
| `totalPrice` | `289` |
| `package_group_id` | The shop's same-day group for 19 October |
| `partnerId`, `customerId`, `maßschaftKollektionId` | `p1`, `c1`, `k1` |

6. After saving: a billing line of 289 with status `panding` is added, and the shop's open amount goes from 1,000 to 1,289. The shop gets the confirmation e-mail, the admins get the new-order e-mail and notice, and the files are copied into Anna Schmidt's file area under `Maßschäfte / Massschafterstellung / 2026-10-05`.
7. The answer is `201` with the order. The order appears in "Aktivität" on the balance page as `#10023`, and in the admin's order list.

What happens next (status, payment, shipping back) continues in the examples of `02.3-custom-shafts-status-and-payment.md` and `02.4-custom-shafts-shipping.md`.
