# Problems found, and the fixes they need

Every problem here was checked in the code. Each one says what really happens, where, and what change is needed. The numbers are fixed so other chapters can point to them; they are not an order of importance. `00-overview.md` sorts them by business effect and says which ones need a direct call to the server.

## 1. Saving or sending a reopened draft deletes the order's own files

**Where:** `updateAdminOrderAfterDraft` in `module/v1/admin_order/custom_shafts.controllers.ts`, the file loop.

**What happens:** When the partner reopens a draft, the page fills the 3D lasts, zipper picture, and paint picture with their saved web addresses and sends them back. For every file field that is sent, the server deletes the old file from storage and then saves the new address. It does not check whether the new address is the same as the old one. So the file is deleted and the order still points at it.

With "Ausführung wie im Katalog", the paint picture address is the catalogue's own leather picture. Sending the draft then deletes the catalogue's picture as well.

**Fix:** Delete the old file only when the address really changed, and only after the database update succeeded.

## 2. A custom-model draft cannot be sent

**Where:** `updateAdminOrderAfterDraft`. `custom_models_image` is in its list of file fields.

**What happens:** The partner's custom-model page sends `custom_models_image` when it saves the draft. The server writes it onto the order row, but the order table has no such column (the picture lives on `custom_models`). The database call fails and the partner gets an error (`500`). The draft cannot be saved again or sent.

**Fix:** Save `custom_models_image` on the order's `custom_models` row, not on the order.

## 3. Deleting an order lowers the open amount even when it should not

**Where:** `deleteCustomShaft` and `deleteCustomShaftAsBulk`.

**What happens:** Deleting lowers the partner's open amount by the full price of the order, whatever its state. The admin's Trash deletes cancelled orders this way.

| Order (price 100) | Before delete | Delete | Result |
| --- | --- | --- | --- |
| Unpaid, cancelled | Create +100, cancel −100 = 0 | −100 | The order is taken off a second time. Because the amount cannot go below 0, the 100 comes off the partner's other open orders. |
| Paid, not cancelled | Create +100, paid −100 = 0 | −100 | Same |

**Fix:** Lower the open amount only for an order that still counts in it, which is a live, unpaid order. A cancelled order was already settled by the cancel step, and a paid order was already taken off by the payment step.

## 4. Deleting an order can delete the catalogue's leather picture

**Where:** `deleteCustomShaft` and `deleteCustomShaftAsBulk` delete every web address found on the order, including `paintImage`.

**What happens:** With "Ausführung wie im Katalog", `paintImage` is the catalogue's own `ledertyp_image` address (set in the partner's browser). Deleting such an order, for example from the Trash, deletes the catalogue's picture from storage. Every other order of that catalogue shoe and the catalogue itself then show a broken picture.

**Fix:** Do not delete files that the catalogue (`maßschaft_kollektion`) still uses. A simpler and safer fix is to copy the catalogue picture into a new file when the order is created, so every order owns its files.

## 5. A discount on a paid order lowers the open amount

**Where:** `updateAdminOrderAsBulk`, the discount part.

**What happens:** Changing the discount moves the open amount by the difference for every order that is not cancelled or neutral, including paid ones. A paid order is no longer in the open amount, so the change lowers the amount of the partner's other orders.

Also, payment (`updatePaymentStatus`) always moves the full `totalPrice`, without the discount. When a discounted order is marked paid, the open amount drops by more than was added for it.

**Fix:** Apply the discount change only to unpaid orders, and use the price minus the discount when payment changes.

## 6. A partner login can set any partner's balance

**Where:** `PATCH /v2/admin-order-transitions/finance/set-0-balance-to-partner/:partnerId`, handler `set0BalanceToPartner` in `module/v2/admin_order_transitions/finance/finance.controllers.ts`.

**What happens:** The route accepts partner and employee logins, and the handler does not check who is calling. A partner can change the open amount of any partner.

**Fix:** Admin only.

## 7. Endpoints without any login

These routes have no `verifyUser`, so anyone who knows the address can call them:

| Address | What it gives or does |
| --- | --- |
| `GET /v3/admin-order/get-all-orders` | All orders of all partners, with prices and profit |
| `GET` and `POST /v3/admin-order/get-child-list` | Child orders |
| `GET /v3/admin-order/get-all-partner` | Partner list |
| All 11 routes of `/v3/admin-order/calculation-info/*` | Open, new, late, in-production, shipped and finished orders, revenue |
| `GET /custom_shafts/treack/get-custom-shafts-status-history/:orderId` | Status history of any order (the login line is commented out) |
| `GET /v3/manufacturer/order/get-by-id/:id` | A manufacturer order with its shaft order and documents |
| `PATCH /v3/manufacturer/order/update-status` | Change manufacturer order status |
| `GET /custom_shafts/damian-count` | The shared number |

**Fix:** `verifyUser("ADMIN")` on every address above except the two producer addresses. Those two get `verifyUser("MANUFACTURER", "ADMIN")`, like the other producer order addresses (`order/get-all`, `order/by-shaft`), and a producer login may only read or change its own `manufacturer_order`.

## 8. File uploads happen before the login check

**Where:** These routes run the file upload before `verifyUser`:

- `PATCH /custom_shafts/update-admin-order-after-draft/:id`
- `POST` and `PATCH /v3/admin-order/manage/uploade-document/:customShaftsId`
- `PATCH /v3/admin-order/admin-to-partner-shipping/update-shipping-data`
- `POST /v3/admin-order/admin-to-partner-shipping/upload-delivery-invoice/:shippingGroupId`

**What happens:** In production the upload writes straight to storage (`config/multer.config.ts`, up to 15 files of 100 MB each). A call without a login is refused afterwards, but the files stay in storage.

**Fix:** Put `verifyUser` before the upload in these routes.

## 9. Order endpoints that do not check the order's owner

These routes accept partner logins but never check that the order belongs to the calling partner. The partner screens only send the partner's own orders, so the risk is a direct call with another partner's order id.

| Address | What another partner could do |
| --- | --- |
| `GET /custom_shafts/get`, `GET /custom_shafts/get/:id` | Read orders |
| `PATCH /custom_shafts/update-status/:id`, `update-status-bulk`, `update-status-base-on-shipping-group` | Change production status |
| `PATCH /custom_shafts/update-payment-status` | Mark orders paid, which changes that partner's balance |
| `DELETE /custom_shafts/delete/:id`, `delete-bulk`, `delete-as-bulk` | Delete orders |
| `POST /custom_shafts/cancel-order/:orderId` | Cancel a new order |
| `PATCH /custom_shafts/update-delivery-date/:id` | Change dates |
| `PATCH /custom_shafts/update-admin-order/:id`, `update-admin-order-as-bulk` | Change costs, discount, order state |
| `POST /massschuhe-order/admin-order/halbprobenerstellung/upload-checkliste/:orderId` | Overwrite the checklist |
| `POST /custom_shafts/leistenerstellung/create` with another partner's feedback or test shoe | Attach a last order to it |
| `POST /custom_shafts/bettungserstellung/create`, `custom-bodenkonstruktion/create` with another partner's `shoe_order_id` | Create an order billed to that partner |
| `POST /custom_shafts/treack/set-invoice`, `GET get-invoice/:invoiceId`, `POST upload-file-to-invoice/:invoiceId` | Put another shop's orders on an invoice, read its VAT number and address, replace its invoice PDF. No partner screen uses these. |
| `POST` and `PATCH /v3/admin-order/manage/uploade-document/:customShaftsId`, `GET /v3/admin-order/manage/get-document/:id` | Read or replace another shop's producer sheets (the old file is deleted). No partner screen uses these. |

**Fix:** Make the admin-only actions (status, payment, delete, admin edits, delivery date) `verifyUser("ADMIN")`. Where partners need the route (cancel, checklist, create), check `partnerId` against the login.

## 10. The manual last order has no order number and no shoe order link

**Where:** `createLeistenerstellungOrder`.

**What happens:** The "Nur Leisten fräsen" order is saved without `orderNumber` and without `shoe_order_id`. The admin notice says "Bestellung #null". The production card (`getProductionCard`) only sees orders linked to the shoe order, so after a reload the care plan no longer shows the last order as chosen, and the partner can order again.

**Fix:** Set the next order number and `shoe_order_id`, as the automatic last order in the feedback already does.

## 11. Some orders store working days as if they were calendar days

**Where:**

- The test shoe (`halbprobenerstellungOrder` and `sendToAdminOrder_1`): `delivery_length` is the category's number as it is, and `deliveryDate` is not set.
- The automatic last order after "no issue" feedback (`createCustomShaftsFeedback`): the same.

**What happens:** Everywhere else, `delivery_length` is stored in calendar days (`resolveAutoDeliveryPlan`). The partner's list and the admin's late-order counts calculate "production start + `delivery_length` calendar days". For a test shoe made from 3D files, or the automatic last order, the expected date therefore comes out too early (10 working days become 10 calendar days), and the order counts as late too early. When the lasts arrive later, the status update recalculates the days correctly.

**Fix:** Use `resolveAutoDeliveryPlan` in these places too, and save its calendar days and date.

## 12. "Done" means different things depending on how it was set

**Where:** See "Every way an order becomes done" in `02.3-custom-shafts-status-and-payment.md`, and the admin→partner job sets `Versandt` without history.

**What happens:** Only the status page writes the status history, completes the shoe order steps, and marks the billing lines `complated`. Marking a whole shipment as done, FedEx delivery, and the delivery invoice upload each do only part of this. The order history and the billing lines then disagree with the status.

**Fix:** One shared function for "set to shipped" and "set to done", used by all of them.

## 13. Sending a draft ignores the shipping prices in the request

**Where:** `sendOrderToAdmin` in `module/v3/admin_order/manage/manage.controllers.ts`.

**What happens:** It reads `shipping_cost1` and `shipping_cost2` from the request but never saves them. The partner's draft page sends the pickup price there. The order keeps the price from the draft.

**Fix:** Save them like `shipping_type1` and `shipping_type2`.

## 14. `/custom_shafts/get` cannot search

**Where:** `getTustomShafts`.

**What happens:** The search looks in fields that do not exist on the order (`lederfarbe`, `innenfutter`, `schafthohe`, `polsterung`, `vestarkungen`, `polsterung_text`, `vestarkungen_text`, `nahtfarbe`, `nahtfarbe_text`, `lederType`), so any search fails. The list also has no partner filter. No screen calls this address.

**Fix:** Remove the route. If it is kept, search real columns and limit partners to their own orders.

## 15. The chat does not check that the order belongs to the shop

**Where:** `sendMessage`, `getMessages`, `markAsRead` in `module/v3/admin_order/chat/chat.controllers.ts`, and the socket event `custom-shafts-chat-room` in `socket/index.ts`.

**What happens:** These take an order id and work with it for any partner login. A direct call with another shop's order id reads that conversation, writes into it, or marks FeetF1rst's messages as read there. A socket that joins another order's room receives its new messages live. The screens only use the shop's own orders, so this needs a direct call. The other chat addresses (`context_info/get`, `assign_employee/*`, `message-reaction`) already check the owner.

**Fix:** Use the same owner check as `context_info/get` (order `partnerId` = the shop of the login; admin may use any order) in these three handlers and before joining the socket room.

## 16. Most chat settings have no effect, and chat messages create no notification

**Where:** `custom_shafts_chat_settings`, saved by the Partner Dashboard settings page (`dashboard/email/einstellungen`).

**What happens:** The page offers these switches and the server saves them, but nothing reads them:

| Setting | What the shop expects | What really happens |
| --- | --- | --- |
| `message_sending_type`, `ask_before_message` | Choose whether the inbox asks who is working | A partner login is always asked, whatever is chosen |
| `confir_id_for_each_message` | Confirm the person before each message | Never asked |
| `selected_employees` | Only selected employees see conversations | The server only reads `all_employees`. When it is off, employees see the conversations given to them, whichever option was picked. |
| The five `notify_…` switches | Notifications for new messages, tags, assignments | No chat notification is created at all. The notification type `custom_shafts_chat` exists but nothing writes it. New messages only show as unread numbers and live updates in an open tab. |

`reset_activity` and `all_employees` are the only chat settings in use.

**Fix:** Decide per switch: build it, or remove it from the settings page until it exists. The notification for a new FeetF1rst message is the one with the clearest business need, because a shop that does not have the inbox open does not learn about an answer.

## 17. Collected invoices can contain the wrong orders, numbers, or totals

**Where:** `setInvoiceData` in `module/v1/admin_order/treack/treack.controllers.ts`, and the PDF button in the admin's `OrderNewTable.jsx`. See `02.7-custom-shafts-invoices-and-emails.md`.

**What happens:**

| Case | Result |
| --- | --- |
| The admin ticks every order of a shop that is on the screen | The screen sends only the shop id. The server then invoices every order of that shop that is not on an invoice, not neutral, and not a draft: also cancelled orders, and orders that were not loaded on the screen. |
| Some ticked orders are already on an older invoice | The server leaves them out, but the screen shows the new invoice on all ticked orders until reload |
| Two invoices are made at the same moment | Both can get the same `invoiceNumber`: it is the highest number + 1, and the column is not unique |
| Some orders of an invoice are deleted later | The invoice keeps its old total and PDF. `get-invoice` then lists fewer products than its total. |

**Fix:** Always send the ticked order ids, and leave cancelled orders out on the server. Make `invoiceNumber` unique and take it from a counter. Recalculate the total (or refuse the delete) when an invoiced order is deleted.

## 18. The admin's count cards disagree with each other

**Where:** `get-calculation-data` and `calculation-info/*` (v3), and `statistics/get-calculations` (v1). See `02.8-custom-shafts-dates-and-counts.md`.

**What happens:**

- "Versandt diesen Monat" counts every order that is still `Versandt`, from any month.
- "Late" is calculated in four ways. The `partnerbestellungen` card needs a production start and only five categories. The `manage-order` card falls back to the creation date and takes every category. So the two pages show different late numbers on the same day.
- "In production" is `In_Produktiony` on `partnerbestellungen`, but every status except `Neu` and `Ausgeführt` on `manage-order`, which also counts received and shipped orders.

**Fix:** One shared definition per card, used by every address. For "shipped this month", filter by `shipping_time` in the current month.

## 19. Partner logins can change settings that apply to every shop

**Where:** `module/v1/admin_order/delivery_dates/delivery_dates.routes.ts` and `module/v1/admin_order/statistics/statistics.routes.ts`.

**What happens:**

| Address | Accepts | Effect |
| --- | --- | --- |
| `POST /custom_shafts/delivery-dates/add-holyday-and-vacation`, `undo-holyday-and-vacation` | Partner, admin, employee | Holidays apply to all shops. Each change re-plans every shop's open orders. |
| `POST /custom_shafts/delivery-dates/manage` | Partner, admin, employee | Changes the working days of a category for everyone |
| `GET /custom_shafts/statistics/get-calculations`, `get-revenue` | Partner, admin, employee | Order counts and revenue of all shops |

Only the admin dashboard calls these. A shop would have to call them directly.

**Fix:** `verifyUser("ADMIN")` on these five addresses.

## 20. A holiday change overwrites delivery dates set by hand

**Where:** `recalcOpenOrdersForBlockedDateChange` in `module/v1/admin_order/delivery_dates/delivery-date-weekend.utils.ts`.

**What happens:** After every holiday change, every open order with a `deliveryDate` is planned again from the category's working days. A date that the admin moved by hand (`update-delivery-date`, or the v3 delivery-date change) is replaced without a message. The v3 delivery-date change also writes only `delivery_length`, not `deliveryDate`, so after it the two disagree: the late count uses the new length, while `suggest-orders-after-3-days` and the re-plan use the old date.

**Fix:** Mark orders whose date was set by hand and leave them out of the re-plan. Let the v3 change save `deliveryDate` too.

## 21. Producer accounts are not protected

**Where:** `module/v3/manufacturer/manufacturer_auth/manufacturer_auth.controllers.ts`, `manufacturer.controllers.ts`, `assaing_order/assaing_order.controllers.ts`.

**What happens:**

| Point | Detail |
| --- | --- |
| Password reset without the code | `sendotp` already sets "allowed to reset" before any code is checked. Calling `sendotp` and then `reset` changes the password of any producer whose e-mail is known. |
| Login without a password | A producer created without a password has an empty password. Login compares `stored !== sent`, so sending an empty password logs in. |
| Passwords in plain text | Saved as typed, and returned by `get-all` (admin) and `auth/profile` |
| Login links never expire | The e-mail link and the login token have no end date |
| A producer can see other producers' orders | `order/get-all` uses `manufacturerId` from the address before the login's own id. `order/by-shaft` returns the producer of any order. |

The two addresses without any login (`order/get-by-id`, `order/update-status`) are in problem 7.

**Fix:** Store password hashes and stop returning them. Check the code in `reset`. Refuse an empty password. Give tokens an end date. For a producer login, always use the login's own id.

## 22. The producer area cannot report progress and shows wrong data

**Where:** `app/(manufacturer_dashboard)/ubersicht/` in the Partner Dashboard app. See "What the producer cannot do" in `02.9-custom-shafts-manufacturer.md`.

**What happens:** No screen sends the producer status, the order detail page shows fixed sample data, the next page never loads (`pagination.cursor` is read instead of `nextCursor`), customer names never appear (`firstName`/`lastName` instead of `vorname`/`nachname`), and the table shows the order's status instead of the producer's, so "needs attention" never finds an order with a question. The admin therefore never learns from the system how far a producer is.

**Fix:** Read the fields the server sends, show the real order on the detail page, and add a status change for the producer (behind a producer login, own orders only).

## 23. Smaller points

| Where | What happens | Fix |
| --- | --- | --- |
| Order with `createLabel=yes` whose FedEx label fails | The admins get no new-order e-mail at all; only the shop gets an in-app "label failed" notice. | Send the new-order e-mail independent of the label. |
| E-mail queue (`cron/email_queue.ts`) | A failed e-mail goes back to "pending" and is tried every minute without end | Count attempts and stop after a few |
| A draft sent later (`send-order-to-admin`) | Its files are never copied into the customer's file area | Call the same copy step when the draft is sent |
| Replacing a producer sheet (`uploade-document`) | The old file is deleted before the new address is saved. If saving fails, the new file is deleted too, and the row still points at the deleted old file. | Delete the old file only after saving |
| Deleting an order | The producer-sheet row and its files stay, with an empty order link | Delete them with the order |
| Deleting a shop | Its invoice rows are deleted, the invoice PDFs stay in storage | Collect and delete the files |
| Chat, deleting an admin or partner account | `custom_shafts_chat.sender` is deleted with the account. Every message that account wrote disappears from every order's conversation, so the other side loses the history. | Keep the message and empty the sender link, as is already done for employees. |
| Chat, deleting an order | The messages, file rows, and assignments stay with an empty order link, and the files stay in storage. Nothing can reach them. | Delete the conversation and its files with the order. |
| `createTustomShafts`, joining a shipment fails | The answer is an error, but the order, its billing line, and the higher open amount already exist. A partner who tries again creates a second order. | Answer success with a shipping warning, or join the shipment before saving the order. |
| `updateCustomShaftStatus` and bulk with `order_status: canceled` | The order is cancelled without changing the open amount. No screen sends this. | Remove `order_status` from these routes; cancelling has its own route. |
| `manage-cancelation` with `active` | A cancelled order becomes live again without the open amount going back up. No screen calls this. | Use the same restore rule as the Trash. |
| Sole create e-mail (`createCustomBodenkonstruktionOrder`) | The admin e-mail shows the date from the request, not the calculated delivery date. | Use the calculated date. |
| `finalizeCustomShaftOrderBilling` | Creating the billing line and raising the open amount are two separate steps. A failure between them leaves a billing line without the amount. | Run both in one transaction. |
