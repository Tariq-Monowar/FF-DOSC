# After the order: status, payment, cancel, edits, delete

This file covers what happens to an order after it was created: the production status, payment, cancelling, the admin's edits, the Trash, and deleting. Unless noted, the handlers are in `module/v1/admin_order/custom_shafts.controllers.ts` and the addresses start with `/custom_shafts`.

## Changing the production status

`PATCH /custom_shafts/update-status/:id`, handler `updateCustomShaftStatus`. Logins: partner, admin, employee.

`PATCH /custom_shafts/update-status-bulk` with `ids` does the same for many orders (`updateCustomShaftStatusBulk`).

The admin dashboard uses both: the order detail page (status workflow) and the order list (multi-select, last arrival).

### Body

| Field | What it does |
| --- | --- |
| `status` | The new production status. Must be a value of the status list, otherwise `400` "Invalid status value". |
| `last_status` | `Angekommen` or `Unangekommen` |
| `order_status` | Optional: `active`, `canceled`, `completed`, `neutral` |

`status` or `last_status` is required.

### Rules

| Change | What the server does |
| --- | --- |
| Status `lasts_received` | Also sets the last to `Angekommen` |
| Last `Angekommen` (without a status) | Orders that are in production, shipped, or done only get the last marked. All others also move to `lasts_received`. |
| Lasts arrive (either case above) | The production clock starts now. `delivery_length` and `deliveryDate` are calculated again from the category's working days. Orders already at `lasts_received` are not recalculated. |
| Any status, while the order is in a quality-control shipping queue | Refused with `400` and the queue's message (`getQcShippingQueueStatusChangeBlock`) |
| Status `Versandt` | `shipping_time` = now, `delivered_at` cleared |
| Status `Ausgeführt` | `delivered_at` = now; `shipping_time` = now if it was empty |
| Any other status | `shipping_time` and `delivered_at` cleared, and an admin→partner FedEx label is voided |
| Billing lines | Status `Ausgeführt` sets the order's billing lines to `complated`; any other status sets them to `panding` |
| Test shoe to `Warten_auf_Anprobe` | A "major issue" feedback on the shoe order is marked expired. The shoe order's test-shoe step is completed and "Halbprobe durchführen" is started. The partner gets "Halbprobenbestellung ist bereit für Anprobe". |
| `Versandt` or `Ausgeführt` | The matching shoe order steps are completed. With `Versandt`, the partner gets "Deine Bestellung #… wurde versandt". |
| `Qualitätskontrolle` | An admin→partner shipment is created or joined (`ensureAdminToPartnerShippingOnQualitätskontrolle`) |
| `order_status: canceled` | The order leaves its shipments. The partner's open amount is **not** changed. No screen sends this. |

Every real change is written to `custom_shafts_status_history`.

Answer: `200` "Custom shaft status updated successfully", with the new statuses.

### Marking a whole shipment as done

`PATCH /custom_shafts/update-status-base-on-shipping-group`, body `shipping_group_id`. The admin's shipping card (`Versand/ShippingPreparationClientCard.jsx`) uses it.

The shipment must be admin→partner. Every order in it that is not done yet gets `Ausgeführt` and `delivered_at` now. Nothing else happens: no history, no billing-line change, no shoe order step, no message.

### Every way an order becomes "done"

| Way | History | Billing lines `complated` | Shoe order steps |
| --- | --- | --- | --- |
| Status page (`update-status`, bulk) | Yes | Yes | Yes |
| Whole shipment (`update-status-base-on-shipping-group`) | No | No | No |
| FedEx says delivered (`cron/fedex.custom-webhook.ts`) | No | No | No |
| Admin uploads the delivery invoice of a shipment (`uploadDeliveryInvoice` in `module/v3/admin_order/admin_to_paerner_shipping/shipping.controllers.ts`) | No | Yes | No |

## Payment

`PATCH /custom_shafts/update-payment-status`, body `ids` and `payment_status` (`Paid`, `Unpaid`, `Unclear`). Handler `updatePaymentStatus`. The admin dashboard uses it.

- Every id must exist, otherwise `400` "Some custom shaft IDs were not found".
- `paid_at` is now for `Paid`, and empty otherwise.
- The partner's open amount moves only when an order changes between paid and not paid. Paid lowers it by the order's `totalPrice`. Leaving paid raises it by the same. It never goes below `0`.

`production_payment_status` (what FeetF1rst pays the production) is separate and is set through the bulk edit below. It does not move the partner's amount.

## Cancelling

### One order

`POST /custom_shafts/cancel-order/:orderId`, handler `cancelAdminOrder`. Logins: partner, admin, employee. The partner cancels from the balance page ("Aktivität" and its tables), the admin through `productsCreate.js`.

| Who | Allowed when |
| --- | --- |
| Admin | Any order that is not cancelled yet |
| Partner or employee | Only when the status is `Neu` or `Bestellung_eingegangen`. Otherwise `403`. |

An order that is already cancelled answers `400` "Order already canceled".

What cancelling does (`commitCancelAdminOrder`), in one transaction:

1. The order leaves its admin→partner shipment. If it was the shipment's main order, the next live order of the same group takes over. The shipment's count goes down, and an empty shipment is deleted.
2. The order leaves its partner→admin shipment the same way.
3. `order_status` becomes `canceled`, and the group and shipment links are cleared.
4. The partner's open amount changes by the sum of the order's billing lines (or `totalPrice` when there are none): an unpaid order lowers it, a paid order raises it.

Then the other side is told: when the admin cancels, the partner gets a message; when the partner cancels, the admins get one.

### Many orders

`POST /custom_shafts/manage-cancelation`, admin only, up to 100 `ids`, `order_status` `canceled` (default), `active`, or `completed`. `canceled` uses the same cancel steps. `active` and `completed` only set the value; they do not change the open amount. No screen calls this address.

## The Trash

The admin's Trash (`feetf1rst-landing-page/src/apis/TrashApis/getTrashApis.js`) shows cancelled orders:

| Action | Address | What it does to money |
| --- | --- | --- |
| List | `GET /massschuhe-order/admin-order/get?order_status=canceled` | None |
| Restore | `PATCH /custom_shafts/update-admin-order-as-bulk` with `order_status: active` | The reverse of cancel: an unpaid order raises the open amount again, a paid order lowers it |
| Delete for good | `DELETE /custom_shafts/delete-as-bulk` | Lowers the open amount by the sum of the billing lines, whatever the payment or cancel state |

## Deleting

`DELETE /custom_shafts/delete/:id` (`deleteCustomShaft`), `DELETE /custom_shafts/delete-bulk`, and `DELETE /custom_shafts/delete-as-bulk` (both `deleteCustomShaftAsBulk`; the last one is partner and admin only).

1. The order and all orders under it (test shoe → last, sample, …) are collected.
2. Every web address in the orders' file columns, inside their JSON specifications, in their custom models, and in their feedback is collected.
3. In one transaction: feedback links cleared, feedback and its files deleted, custom models deleted, billing lines deleted, the partner's open amount lowered by the sum of the billing lines (never below `0`), the orders deleted, and an invoice deleted when no other order uses it.
4. After that, all collected files are deleted from storage.

A file shared with something else is deleted too. With "Ausführung wie im Katalog", the order's `paintImage` is the catalogue's own leather picture (see `02.1-custom-shafts-shaft-and-complete-shoe.md`), so deleting the order deletes that picture.

## Admin edits

### One order: costs, shipping, production number, pickup label

`PATCH /custom_shafts/update-admin-order/:id`, handler `updateAdminOrder`, with an optional file `pickup_label`.

| Field | Saved to |
| --- | --- |
| `productionCost` | `production_cost` |
| `shipping_cost1`, `shipping_cost2`, `shipping_type1`, `shipping_type2` | The same columns |
| `production_number` | `production_number`; empty clears it |
| `production_payment_status` | `Paid`, `Unpaid`, `Unclear`, or empty |
| `pickup_label` | A file, a web address, or empty to remove. Sets or clears `label_created_at`. |

A replaced or removed label file is deleted from storage afterwards. A new label tells the partner "Wir haben dein Schuhetikett erhalten".

### Many orders

`PATCH /custom_shafts/update-admin-order-as-bulk`, body `ids` plus any of:

| Field | Rule |
| --- | --- |
| `productionCost`, `shipping_cost1`, `shipping_cost2` | Numbers, or empty to clear |
| `shipping_type1`, `shipping_type2` | Text |
| `production_payment_status` | `Paid`, `Unpaid`, `Unclear`, or empty |
| `production_number` | Text, or empty |
| `urgency` | `normal` or `urgent` |
| `discount` | `0`–`100`, or empty to clear |
| `delivery_length` | Whole number `0` or more |
| `order_status` | A valid value. `active` on a cancelled order is the Trash restore above. `canceled` removes the orders from their shipments but does not change the open amount. |
| `production_start_date`, `shipping_time` | Dates, or empty to clear |

A discount change moves the open amount by the old discount minus the new discount, for every order that is not cancelled or neutral. Delivery notes take the discount off the price as an amount (`price − discount`).

The admin dashboard uses this for production cost, production number, production payment, discount, urgency, and the Trash restore. The partner dashboard has a wrapper for it (`updateAdminOrdersAsBulk` in `apis/customShaftsApis.ts`) that no screen calls.

### Delivery date

| Address | Who | What it changes |
| --- | --- | --- |
| `PATCH /custom_shafts/update-delivery-date/:id` | Partner, admin, employee | `deliveryDate` as sent, and `delivery_length` when sent |
| `PATCH /v3/admin-order/delivery-date-change/update-delivery-date/:customShaftsId` | Admin | Writes a `delivery_date_change` row (new date, time, reason, note, how to tell the partner), sets `delivery_length` to the days from production start to the new date, and tells the partner by e-mail or in the app when chosen. The date may not be in the past or before production start. `deliveryDate` is not changed. |
| `GET /v3/admin-order/delivery-date-change/get-history/:customShaftsId` | Admin, partner, employee | The list of changes |

### Other small edits

| Address | Who | What it does |
| --- | --- | --- |
| `PATCH /v3/admin-order/production-handover/:orderId` | Admin | Sets `handover` (`not_prepared`, `sheet_generated`, `sent_to_production`), `handover_by`, and `handover_sent_at` when sent |
| `PATCH /v3/admin-order/manage/update-bg-colore/:customShaftsId?colore=` | Admin, partner (own order only) | Sets or clears the row colour `bg_colore` |
| `PATCH /v3/admin-order/manage/update-order/:customShaftsId` | Admin, partner (own order only) | Edits a neutral order: pickup address, shipping, sample sending date, production start, delivery length |
| `PATCH /v3/admin-order/billing-month/update-billing-month` | Admin | Moves orders to another billing month |
| `POST /custom_shafts/manage/damian-count` | Admin | Saves one shared number (`damian_count`). `GET /custom_shafts/damian-count` reads it, without login. |

## A worked example: the open amount through one month

The shop "Orthopädie Weber" starts with an open amount (`partner_total_amount`) of 1,000. Each line shows the step, the address the screen calls, and the open amount after it.

| Step | Address | Open amount |
| --- | --- | --- |
| Shaft `10023` is ordered for 289 (see `02.1`) | `POST /custom_shafts/create` | 1,289 |
| Admin marks `10023` as `Paid` | `PATCH /custom_shafts/update-payment-status` | 1,000 |
| Shop orders a sole `10026` for 120 | `POST /custom_shafts/custom-bodenkonstruktion/create` | 1,120 |
| Shop cancels `10026` while it is still `Bestellung_eingegangen` | `POST /custom_shafts/cancel-order/:orderId` | 1,000 |
| Admin restores `10026` from the Trash | `PATCH /custom_shafts/update-admin-order-as-bulk` with `order_status: active` | 1,120 |
| Admin cancels `10026` again | `POST /custom_shafts/cancel-order/:orderId` | 1,000 |
| Admin deletes `10026` for good from the Trash | `DELETE /custom_shafts/delete-as-bulk` | 880 |

The last line is problem 3 in `02.5-custom-shafts-problems.md`. The cancelled order was already taken off the amount, and the delete takes its 120 off a second time, from the shop's other orders.

Order `10023` meanwhile moves through the status page: `lasts_received` → `In_Produktiony` → `Qualitätskontrolle` (an admin→partner shipment is made) → `Versandt` → `Ausgeführt`. Each change writes a line in `custom_shafts_status_history`. With `Ausgeführt` from the status page, its billing line becomes `complated`.
