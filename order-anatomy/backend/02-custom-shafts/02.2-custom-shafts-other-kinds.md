# The other orders: test shoe, sample, last, insole, sole

`02.1-custom-shafts-shaft-and-complete-shoe.md` covers the shaft and the complete shoe. This file covers every other way a `custom_shafts` row is created, and the fitting feedback that connects them.

All of them save into the same table, with the same order number rule (next number per partner, from `10000`) unless a section says otherwise.

## Which screen creates which order

| Order | Server address | Handler | Partner screen |
| --- | --- | --- | --- |
| Test shoe (`Halbprobenerstellung`) | `POST /massschuhe-order/admin-order/halbprobenerstellung/create` | `halbprobenerstellungOrder` in `module/v1/massschuhe_order/admin_order/admin_order.controllers.ts` | `dashboard/leistenkonfigurator` |
| Test shoe from a Maßschuh order | `POST /massschuhe-order/admin-order/send-to-admin-1/:orderId` | `sendToAdminOrder_1`, same file | `massschuhauftraege-deatils/1` (`ShoeDetails.tsx`) |
| Sample (`Probenerstellung`) | `POST /custom_shafts/probenerstellung/create` | `createProbenerstellungOrder` | Step 4 of the new Maßschuh order (`HalbprobenerstellungStepFields.tsx`) |
| Last (`Leistenerstellung`), by hand | `POST /custom_shafts/leistenerstellung/create` | `createLeistenerstellungOrder` | "Nur Leisten fräsen" on the care plan (`FeetF1rstContinueSection.tsx`), the Maßschuh order page, and the release window (`FreigebenFlowModal.tsx`) |
| Last, automatic | Inside the fitting feedback | `createCustomShaftsFeedback` in `module/v1/admin_order/feedback/feedback.controllers.ts` | The partner gives feedback "no issue" |
| Last, silent | Inside the shaft order | `createTustomShafts` | A shaft order that follows a fitting feedback |
| Insole (`Bettungserstellung`) | `POST /custom_shafts/bettungserstellung/create` | `createBettungserstellungOrder` | No screen in the partner dashboard calls it |
| Sole (`Bodenkonstruktion`) | `POST /custom_shafts/custom-bodenkonstruktion/create` | `createCustomBodenkonstruktionOrder` | `dashboard/bodenkonstruktion` and the care plan's sole form |
| Sole from a Maßschuh order | `POST /massschuhe-order/admin-order/send-to-admin-3-order/:orderId` | `sendToAdminOrder_3` | `massschuhauftraege-deatils/2` (`Bodenkonstruktion.tsx`) |
| Shaft or complete shoe from a Maßschuh order | `POST /massschuhe-order/admin-order/send-to-admin-2-order/:orderId` | `sendToAdminOrder_2` | `massschuhauftraege-deatils/2` (`Bodenkonstruktion.tsx`) |

"Maßschuh order" here means the older `massschuhe_order` record. When the sole page is opened with an `orderId` of such a record, it sends through `send-to-admin-2` or `send-to-admin-3`. Without it, it sends through `/custom_shafts/create`.

## Test shoe (`Halbprobenerstellung`)

A test shoe is a first shoe the customer tries on before the real one is made.

### What the partner sends

| Field | What it is |
| --- | --- |
| `customerId` or `other_customer_name` | Required, one of them. When missing, `customerId` is also read from `Halbprobenerstellung_json.kopfdaten.customerId`. |
| `other_customer_number` | Customer number |
| `totalPrice` | Required, more than `0` |
| `Halbprobenerstellung_json` | The test-shoe specification |
| `last_type` | `gross_last` (default) or `net_last` |
| `modulation_by` | `feetf1rst` (default) or `internal` |
| `testing_shoe` | Yes/no, default no |
| `delivery_length` | Optional. When missing, the category setting is used. If neither exists: `400`. |
| `shoe_order_id` | Optional. Must belong to this partner, otherwise `404` "shoe_order_id not found for this partner". |
| `custom_shafts_feedback_id`, `clinica_assistant_order_components_id` | Optional links |
| Files `image3d_1`, `image3d_2`, `invoice`, `invoice2`, `Halbprobenerstellung_pdf` | File or web address |

Logins allowed: partner and employee.

### What is saved

- Category `Halbprobenerstellung`, the default status `Bestellung_eingegangen`.
- `delivery_length` is the category's number as it is, in working days. No `deliveryDate` is set.
- `production_start_date` is the creation time when 3D files came with the order. Otherwise empty.
- No `production_number` is set.
- The billing month is set.

### What happens next

1. **Shoe order link.** If no shoe order was sent but a customer was, the server links an open shoe order of that partner and customer that has no live test shoe yet.
2. **Shoe order steps.** The shoe order is marked "last made externally" and "test shoe made externally", and its "Leistenerstellung" step is started.
3. **Balance.** A billing line with the price is created and the partner's open amount goes up. These run directly in the request, not through `finalizeCustomShaftOrderBilling`.
4. **E-mail** to the admins, and a line in the customer's history.

Answer: `200` "Order sent to admin 1 successfully".

### Test-shoe checklist

The partner (or an employee) can save a checklist on the test shoe:

- `POST /massschuhe-order/admin-order/halbprobenerstellung/upload-checkliste/:orderId` saves `checkliste_halbprobe`.
- `GET /massschuhe-order/admin-order/halbprobenerstellung/get-checkliste/:orderId` reads it.

The partner uses it in `HalbprobenerstellungModal.tsx` on the balance page.

### Test shoe from a Maßschuh order

`send-to-admin-1` does the same for an older Maßschuh order. It links the test shoe to that `massschuhe_order`, marks the Maßschuh order as pending, and does not link a shoe order.

## Sample (`Probenerstellung`)

A sample is made for a shoe order. The partner orders it in step 4 of a new Maßschuh order.

| Rule | Detail |
| --- | --- |
| `shoe_order_id` | Required. Must belong to this partner. |
| `totalPrice` | Required, more than `0` |
| One at a time | If the shoe order already has a live sample, the answer is `409` "You have already sent a Probenerstellung to the admin. Please cancel it before creating another one." (German when the server language is German). |
| Delivery plan | Calculated from the category's working days when 3D files are there, as for the shaft |
| Saved | Category, price, files, order number, delivery plan, same-day group, optional feedback link, billing month. No customer and no production number are saved on the row. The shoe order link is written right after. |
| Shoe order | Marked "last made externally" |
| Balance | Billing line and open amount, in the background |
| E-mails | To the admins, and the confirmation to the partner |

Answer: `200` "Probenerstellung order created successfully".

## Last (`Leistenerstellung`)

A last order asks FeetF1rst to mill only the lasts. It always belongs under a test shoe.

### By hand

`POST /custom_shafts/leistenerstellung/create`. Body: `feedback_id`, `sample_id` (or `custom_shafts_id`), `shoe_order_id`. At least one is required.

How the server finds the test shoe:

1. If a feedback is given, the feedback's test shoe. A different `sample_id` answers `400` "sample_id does not match this feedback".
2. Otherwise the given `sample_id`.
3. Otherwise the newest live test shoe of the shoe order.
4. If none is found: `400`.

What is saved:

| Column | Value |
| --- | --- |
| `totalPrice` | `0` |
| `catagoary` | `Leistenerstellung` |
| `parent_custom_shafts_id` | The test shoe |
| Customer, customer name and number | Copied from the test shoe |
| `deliveryDate`, `delivery_length` | Calculated from the category's working days; when that gives no date, the test shoe's date |
| `custom_shafts_feedback_id` | When a feedback was given |
| `orderNumber`, `production_number`, `shoe_order_id` | Not set |

After saving: the test shoe moves to `Leisten_wird_gefräst` if it was waiting for fitting, a line is added to the shoe order history, the admins get an in-app and push notice, and a line is added to the customer's history. There is no billing line, because the price is `0`.

Answer: `200` "Leistenerstellung order created successfully".

### Automatic, after "no issue" feedback

When the partner gives the feedback "no issue" for a test shoe that belongs to a shoe order, and that test shoe has no last order yet, the feedback creates one. It has an order number, the shoe order link, the feedback link, `production_start_date` now, status `Bestellung_eingegangen`, price `0`, and `delivery_length` set to the category's working days as they are. It has no `deliveryDate`.

### Silent, inside a shaft order

See step 4 in "What happens after the row is saved" in `02.1-custom-shafts-shaft-and-complete-shoe.md`.

### Asking for access

`POST /custom_shafts/request-for-leistenerstellung/access`. Logins: partner, admin. It sends the admins an e-mail and a notice that this partner wants to use last ordering. It changes nothing in the database. The partner sends it from `LeistenkonfiguratorDeactiveModal.tsx`.

## Production card

`GET /custom_shafts/production-card?shoe_order_id=…`. Logins: partner, admin, employee. A partner only sees their own shoe order.

It answers which FeetF1rst production choice is already taken for the shoe order, looking only at live orders linked to that shoe order:

| Live orders on the shoe order | `active` |
| --- | --- |
| A complete shoe | `Leistenerstellung + Komplettfertigung` |
| A shaft | `Leistenerstellung + Massschafterstellung` |
| A last | `Leistenerstellung` |
| None | empty |

The care plan's continue section (`FeetF1rstContinueSection.tsx`) uses this to mark the chosen card.

## Insole (`Bettungserstellung`)

`POST /custom_shafts/bettungserstellung/create`. It has no delivery date and no delivery length.

| Field | What it is |
| --- | --- |
| `shoe_order_id` | Optional. When given, the order is billed to that shoe order's partner. |
| `customerId` (or `customer_id`), `other_customer_name`, `other_customer_number` | Optional. When missing, taken from the shoe order or its newest live test shoe. |
| `bettungserstellung_json` | The insole specification |
| `urgency` | `urgent` or `normal` (default) |
| `totalPrice` | Optional |
| `invoice` | File or web address |
| `clinica_assistant_order_components_id` | Optional link |

Saved with status `Bestellung_eingegangen`, an order number, a production number, the newest live test shoe of the shoe order as parent, and the billing month. The shoe order's insole step is started. Billing goes through `finalizeCustomShaftOrderBilling`. Admins get an in-app and push notice.

Answer: `200` "Bettungserstellung order created successfully".

## Sole (`Bodenkonstruktion`)

`POST /custom_shafts/custom-bodenkonstruktion/create`. Add `?is_draft=yes` for a draft.

| Rule | Detail |
| --- | --- |
| `totalPrice` | Required and more than `0`, except for a draft |
| `bodenkonstruktion_json` | Required, except for a draft |
| `delivery_length` | From the body or the category setting. If neither, `400`, except for a draft. |
| `deliveryDate` | Optional. A bad date answers `400` "Invalid deliveryDate format". |
| `shoe_order_id` | Optional. When given, the order is billed to that shoe order's partner. Unknown id: `404`. |
| `customer_id`, `other_customer_name`, `other_customer_number` | Optional |
| `custom_shafts_feedback_id` | Optional. When its test shoe is waiting for fitting, the test shoe moves to `Leisten_wird_gefräst`. |
| Files `invoice`, `staticImage`, `threeDFile` | File or web address |

Saved with `isCustomBodenkonstruktion: true`, an order number, a production number, no production start, and the delivery plan.

For a sent order: the shoe order is marked "sole made externally" and its "Bodenerstellen" step is started, billing goes through `finalizeCustomShaftOrderBilling`, the admins and the partner get e-mails, the files are copied into the customer's file area ("Drive", see `02.7`), and the admins get a notice.

A draft answers `201` "Draft saved successfully" and skips billing, e-mails, and the shoe order steps.

### Sole from a Maßschuh order

`send-to-admin-3-order/:orderId` creates a sole for an older Maßschuh order. It links the `massschuhe_order`, sets order and production numbers, and adds the billing line and open amount directly.

## Shaft or complete shoe from a Maßschuh order

`send-to-admin-2-order/:orderId` creates a shaft, or a complete shoe when both specifications are sent. It links the `massschuhe_order` or a shoe order, the catalogue shoe, the test shoe and feedback when given, and creates the `custom_models` row for a custom model. The status is `Bestellung_eingegangen` even when 3D files are there. It adds the billing line and open amount directly.

## Fitting feedback

After the customer tries the test shoe, the partner records feedback with `POST /custom_shafts/feedback/create`. There are three categories:

| Category | Effect on the test shoe | Other effects |
| --- | --- | --- |
| `MAJOR_ISSUE` | Every live test shoe of the shoe order goes back to `Bestellung_eingegangen`, with status history | Every sample of the shoe order is marked expired (`isExpaired`) |
| `MINOR_ISSUE` | If waiting for fitting, it moves to `Leisten_wird_gefräst`, with status history | When the test shoe has `modulation_by: internal`, the shoe order's "Halbprobe durchführen" step waits until the partner uploads the corrected last |
| `NO_ISSUE` | Same as minor | The shoe order gets a "Nacharbeit" step marked for printing, and the automatic last order above is created |

Deleting a feedback puts the test shoe back to `Warten_auf_Anprobe`.

## A worked example: test shoe, fitting, automatic last

The shop "Orthopädie Weber" (partner `p1`) has a shoe order `so1` for its customer Anna Schmidt (`c1`). The shop's highest order number is `10023`. The admin has set 10 working days for test shoes.

1. On Monday, 5 October 2026, the shop orders a test shoe from `dashboard/leistenkonfigurator`, with both 3D files, price 150, and `shoe_order_id` `so1`.
2. The new row:

| Column | Value |
| --- | --- |
| `orderNumber` | `10024` |
| `catagoary` | `Halbprobenerstellung` |
| `status` | `Bestellung_eingegangen` |
| `production_start_date` | 5 October 2026 (3D files came with the order) |
| `delivery_length` | `10`, the working days as they are |
| `deliveryDate` | Empty |
| `production_number` | Empty |
| `billing_month` | 1 October 2026 (5 October + 10 days = 15 October) |
| `shoe_order_id` | `so1` |

   The partner's list adds 10 calendar days to the start and shows 15 October. Counted in working days it would be 19 October. This is problem 11 in `02.5-custom-shafts-problems.md`.

3. A billing line of 150 is created and the shop's open amount goes up by 150. The shoe order is marked "last made externally" and "test shoe made externally". The admins get an e-mail. The answer is `200` "Order sent to admin 1 successfully".
4. FeetF1rst builds the test shoe. The admin sets the status to `Warten_auf_Anprobe`. The shop gets "Halbprobenbestellung ist bereit für Anprobe", and the shoe order's "Halbprobe durchführen" step starts.
5. Anna tries the shoe on and it fits. The shop records feedback `NO_ISSUE` on `10024`.
6. The test shoe moves to `Leisten_wird_gefräst`, with status history. The shoe order gets a "Nacharbeit" step marked for printing.
7. Because `10024` belongs to `so1` and has no last order yet, the feedback creates the last order:

| Column | Value |
| --- | --- |
| `orderNumber` | `10025` |
| `catagoary` | `Leistenerstellung` |
| `status` | `Bestellung_eingegangen` |
| `totalPrice` | `0` |
| `parent_custom_shafts_id` | The test shoe `10024` |
| `custom_shafts_feedback_id` | The new feedback |
| `shoe_order_id` | `so1` |
| `production_start_date` | The time of the feedback |
| `delivery_length` | The last category's working days, as they are |
| `deliveryDate` | Empty |

   No billing line is made, because the price is `0`.
