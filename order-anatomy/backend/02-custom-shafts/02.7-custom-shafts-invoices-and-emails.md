# Documents, collected invoices, e-mails, and customer files

An order produces paperwork: the producer sheets for the factory, the collected invoice that FeetF1rst sends a shop, the e-mails to both sides, and copies of the order files in the customer's file area. This file covers all four.

Shipping paperwork (label, Lieferschein, delivery invoice) is in `02.4-custom-shafts-shipping.md`.

## Producer sheets (`custom_shafts_document`)

FeetF1rst gives the factory a PDF that describes the order. The row holds the files for one order.

| Column | Meaning |
| --- | --- |
| `custom_shafts_id` | The order. One row per order (unique). If the order is deleted, this becomes empty and the row stays. |
| `massschuhe_manufacturer_pdf` | Producer sheet. Required before the order can be given to a producer (see `02.9-custom-shafts-manufacturer.md`). |
| `massschuhe_manufacturer_pdf2` | Second producer sheet |
| `qualitatskontrolle_invoice` | Quality-check invoice. No code writes it. |

The server does not make these PDFs. The admin dashboard reads the order data from two addresses (`apis/productsCreate.js`), makes the PDF, and uploads it (`apis/subAdmin/partnerbestellungen/manufacturerDocumentApis.js`). The producer area of the Partner Dashboard app reads the same data addresses.

| Address | Logins | What it gives or does |
| --- | --- | --- |
| `GET /custom_shafts/treack/pdf1-data/:orderId`, `pdf2-data/:orderId` | Any login | The order data for sheet 1 and sheet 2 |
| `POST /v3/admin-order/manage/uploade-document/:customShaftsId` | Admin, partner | Uploads files `pdf` and `pdf2` and creates or updates the row. `201` the first time, `200` after. |
| `PATCH` on the same address | Admin, partner | Same, but `404` when no row exists yet |
| `GET /v3/admin-order/manage/get-document/:id` | Admin, partner | Reads the row |
| `GET /v3/admin-order/track/get-document/:id` | Admin | Reads the row |

Files are stored in S3 at the top of the bucket, named `<time>-<file name>`. When a sheet is replaced, the old file is deleted.

## Collected invoice (`custom_shafts_invoice`)

The admin can put several orders of one shop on one invoice. This is the "PDF" button in the admin's order table (`components/dashboard/ManageOrders/OrderNewDesign/OrderNewTable.jsx`). The Partner Dashboard does not use it.

| Column | Meaning |
| --- | --- |
| `invoiceNumber` | Text with digits. Starts at `10000`. The next invoice gets the highest number in the whole table + 1, for all shops together. Not unique in the database. |
| `totalPrice` | Sum of the orders' `totalPrice` when the invoice was made. Never updated later. |
| `invoice` | Address of the PDF |
| `partnerId` | The shop. If the shop account is deleted, this becomes empty. |
| Orders | Every order with `custom_shafts_invoice_id` pointing here. If the invoice is deleted, that link becomes empty. |

### How the admin makes one

1. The admin ticks orders of one shop and clicks the PDF button.
2. `POST /custom_shafts/treack/set-invoice` (`setInvoiceData`). Body: `orderIds`, or only `partnerId` when every order of that shop on the screen is ticked.
   - The same id twice: `400`. Orders of two shops: `400`. Unknown ids: `400` or `404`.
   - The server takes the shop's orders that are not neutral, not drafts, and not on an invoice yet (only the ticked ones when `orderIds` is sent).
   - None left: `200` "All selected orders are already invoiced", with no invoice.
   - Otherwise, in one transaction: the next invoice number, the total, the invoice row, and the orders linked.
   - Answer: `200` "Invoice selection saved successfully" with `invoiceId`, `invoiceNumber`, `totalPrice`, and one product line per order (category as the name, quantity 1, price).
3. `GET /custom_shafts/treack/get-invoice/:invoiceId` (`getInvoiceData`) returns the data for the PDF: the FeetF1rst logo, the shop's business name, VAT number and main store address, the product lines, and the total.
4. The browser builds the PDF (`InvoicePdfGenerator.jsx`).
5. `POST /custom_shafts/treack/upload-file-to-invoice/:invoiceId` (`uploadFileToInvoice`) stores the file and deletes the previous one.
6. The order table shows the invoice link on the orders.

All three addresses accept partner, admin, and employee logins.

### When orders or shops are deleted

- Deleting orders (`delete`, `delete-bulk`, `delete-as-bulk`): when no order is left on an invoice, the invoice row and its PDF are deleted. When some orders are left, the invoice keeps its old total and PDF.
- Deleting a shop (`utils/partner-delete.service.ts`): its invoice rows are deleted. The PDF files stay in storage.

## E-mails

E-mails go out through Gmail (`NODE_MAILER_USER`, `NODE_MAILER_PASSWORD`). Outside production nothing is really sent. "Admins" below means the internal address `INTERNAL_NOTIFY_TO` (the mail account itself, or `info@feetf1rst.com`).

Some e-mails are sent at once. The others are put in a queue (`email_queue`) that a job sends every minute (`cron/email_queue.ts`). A queued e-mail that fails is set back to "pending" and tried again the next minute, without a limit.

| E-mail | To | Subject | Sent | When |
| --- | --- | --- | --- | --- |
| New order | Admins | "FeetF1rst Neue Bestellung – <category>" | At once | A sent shaft, complete shoe, sole, sample, or test shoe, including the older Maßschuh-order routes. With pickup shipping it includes the address, label, and tracking. Last and insole orders only give an in-app notice. |
| Order confirmation | The shop | "FeetF1rst Bestellbestätigung – Auftrag eingegangen" | Queue | Shaft, complete shoe, sole, sample, and a draft when it is sent |
| Pickup organised | The shop | "FeetF1rst Abholung organisiert[ – Tracking …]", with the label PDF attached | Queue | When the FedEx pickup label for the lasts is made |
| Fitting feedback | Admins | "FeetF1rst – Feedback <category> (<order>)" | At once | A feedback on an order |
| Lieferschein | The shop | "FeetF1rst Lieferschein – Bestellung versandt[ (Tracking …)]" | Queue | When FeetF1rst ships to the shop |
| Invoice | The shop | "Ihre Rechnung zu den ausgeführten Bestellungen FeetF1rst" | Queue | When the admin uploads the delivery invoice of a shipment |
| Delivery date changed | The shop | "FeetF1rst – Liefertermin aktualisiert[ – Bestellung …]" | Queue | When the admin changes the date and chooses e-mail |
| Order given to producer | The producer | "FeetF1rst – Nuovo ordine assegnato …" (Italian) | At once | When the admin gives an order to a producer |
| Last ordering access | Admins | "FeetF1rst – Anfrage: Zugang Leistenerstellung" | At once | A shop asks for access to last ordering |

No e-mail is sent for a draft, a status change, a cancellation, or a delete. Two senders exist without any caller: "order shipped" (`sendPartnerOrderShippedEmail`) and "pickup label received" (`sendAdminPickupLabelReceivedEmail`).

## Copies in the customer's file area ("Drive")

The Partner Dashboard has a file area per customer, shown as "Drive". It is not Google Drive. It is the app's own `folder` and `file` tables, with the files in S3 (`prisma/customer-folder.schma.prisma`).

After a shaft, complete shoe, or sole order is sent, `scheduleMasschaftDrive` copies that request's files into the customer's area:

| Item | Detail |
| --- | --- |
| When | Only for an order with a customer, from `/custom_shafts/create` (shaft, complete shoe) and `/custom_shafts/custom-bodenkonstruktion/create` (sole). The shoe-order steps (`module/v2/shoe_orders/order_step`) use the same function. |
| Folder | `Maßschäfte` → category → date of the day (`YYYY-MM-DD`) |
| Files | 3D lasts, invoices, paint, zipper and leather pictures, custom-model picture, sole picture and 3D file; only those sent in that request |
| Timing | After the answer has gone to the shop |
| Failure | The order is not affected. Copies made before the failure are removed again. Nothing is logged. |

Not copied: test shoes, samples, lasts, insoles, the older Maßschuh-order routes, the producer sheets, and a draft that is sent later through `send-order-to-admin`.

## A worked example: one invoice for two orders

The shop "Orthopädie Weber" has two finished orders, `10023` (289) and `10027` (150), on no invoice. The highest invoice number in the system is `10041`.

1. The admin ticks both orders and clicks the PDF button. The table sends `POST /custom_shafts/treack/set-invoice` with `orderIds: [id of 10023, id of 10027]`.
2. The server creates invoice `inv1` with `invoiceNumber` `10042`, `totalPrice` 439, and `partnerId` of the shop. Both orders now point at `inv1`.
3. The table reads `get-invoice/inv1`, builds the PDF, and uploads it. `inv1.invoice` now holds the PDF address.
4. Later the admin deletes order `10027` from the Trash. One order is still on `inv1`, so the invoice stays, still with `totalPrice` 439 and the PDF that lists both orders. `get-invoice/inv1` now lists one product but a total of 439.
