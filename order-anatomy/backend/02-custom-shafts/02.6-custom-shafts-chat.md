# Chat about an order

Every order can have its own conversation between FeetF1rst and the partner's shop. This file covers that chat: who writes, who reads, how unread counts work, which employees see which conversation, the partner's chat settings, and the live updates.

It does not cover the reference-shoe support chat (`/v3/reference-shoe-support-chat`). That is a different chat about support tickets, not about orders.

The tables are in `prisma/admin-order.schma.prisma`, lines 1140–1320. The code is in `module/v3/admin_order/chat/`. Every address starts with `/v3/admin-order/chat`.

## The story, in order

1. A question comes up about an order: a material is missing, a measurement looks wrong, a date must move.
2. On the Partner Dashboard, the shop opens **E-Mail → Inbox** (`dashboard/email/inbox`), or the message button on an order in the balance page's "Aktivität" table (`OrderMessageModal`).
3. When a partner login opens the inbox, the screen first asks who is working right now (`dashboard/email/inbox/select`). The person picks an employee, or continues as the shop itself.
4. They pick an order that already has a conversation, or start a new one with "New message", which lists orders without a chat yet.
5. They write text, attach files, reply to a message, react with an emoji, or tag a colleague with `@Name`.
6. FeetF1rst's team sees the message in the admin dashboard, under **Partnerbestellungen → Nachrichten** (`PartnerbestellungenNachrichtenInbox.jsx`), and answers there.
7. Both sides see a red unread number. Opening the conversation sets it back to zero.
8. The shop owner can give one conversation to specific employees, and decide in the settings whether every employee sees every conversation.

## Who is the sender

Each message stores two people: the account that is logged in (`sender_id`) and, when a shop employee wrote it, that employee (`employee_id`). `sender_role` says which side wrote it.

| Logged in as | `employee_id` in the request | Saved `sender_role` | Saved employee |
| --- | --- | --- | --- |
| Admin | Ignored | `ADMIN` | None |
| Partner | Not sent | `PARTNER` | None |
| Partner | Sent | `EMPLOYEE` | That employee |
| Employee | Sent or not | `EMPLOYEE` | The one sent, otherwise the one in the login |

In this chat, partner and employee messages are one side, the shop. Admin messages are the other side, FeetF1rst.

## What is stored

### One message (`custom_shafts_chat`)

| Column | Meaning | Notes |
| --- | --- | --- |
| `id` | Message id | Text id (cuid) |
| `custom_shafts_id` | The order this message belongs to | If the order is deleted, this becomes empty and the message stays |
| `sender_id` | The logged-in account | If that account is deleted, the message is deleted too |
| `employee_id` | The shop employee who wrote it | Empty for admin and plain partner messages |
| `sender_role` | `ADMIN`, `PARTNER`, or `EMPLOYEE` | Uses the same list of values as the support chat (`reference_shoe_ticket_message_role`) |
| `message_type` | `normal` or `attachment` | `attachment` when at least one file is sent. The list also has `order_tag` and `customer_tag`; no code writes them. |
| `message` | The text | Trimmed. Empty when only files are sent. |
| `isRead`, `read_at` | Whether the other side has read it, and when | Set by "mark as read" |
| `reply_to_id` | The message this one answers | Must be in the same order |
| `createdAt`, `updatedAt` | Times | |

Index: `custom_shafts_id, createdAt desc, id desc`. This is the order in which a conversation is loaded.

### Files on a message (`custom_shafts_chat_attachment`)

| Column | Meaning |
| --- | --- |
| `custom_shafts_chat_id` | The message |
| `file_url` | Public address of the file |
| `file_type` | For example `image/jpeg` |

The server does not receive files in the chat. The Partner Dashboard first uploads each file straight to S3, into the folder `admin-order/chat`, using its own upload address (`/api/s3-presign`). Then it sends only the file addresses. Up to 30 files per message are kept; more are dropped.

### Emoji reaction (`custom_shafts_chat_reaction`)

One reaction per message (`custom_shafts_chat_id` is unique). Who reacted is not stored. A new reaction replaces the old one, from either side.

### Tagged colleagues (`custom_shafts_chat_mention`)

| Column | Meaning |
| --- | --- |
| `custom_shafts_chat_id` | The message. Deleted with the message. |
| `employee_id` | The tagged employee |
| `name` | The name as written after `@` |
| `sort` | Position of the tag in the text, starting at 0 |

Up to 20 tags per message are kept.

### Employees given a conversation (`custom_shafts_chat_employee`)

One row per order and employee. The same employee cannot be added twice to one order. This list decides who sees the conversation when the shop has turned off "all employees see everything" (see below).

### Shop chat settings (`custom_shafts_chat_settings`)

One row per partner, created the first time the partner saves the settings.

| Setting | Label on the settings page | Default | Used by |
| --- | --- | --- | --- |
| `message_sending_type` | How the sender is chosen: by login (`by_auth_token`) or by picking a person (`by_user_id`) | `by_auth_token` | Saved and shown only |
| `confir_id_for_each_message` | Confirm the sender before each message to FeetF1rst | `false` | Saved and shown only |
| `ask_before_message` | Ask who is working when the messages are opened | `false` | Saved and shown only |
| `reset_activity` | After this many minutes without activity, the person must be picked again | `30` | Partner Dashboard inbox: when a partner login chats as an employee, it switches back to the shop account after this time |
| `all_employees` | All employees see FeetF1rst conversations | `true` | Server: conversation lists for employees |
| `selected_employees` | Only selected employees see them | `false` | Saved and shown only |
| `notify_new_feetf1rst_message` | Notify on a new message from FeetF1rst | `true` | Saved and shown only |
| `notify_new_internal_message` | Notify on a new internal message | `true` | Saved and shown only |
| `notify_message_assigned` | Notify when a conversation is given to an employee | `true` | Saved and shown only |
| `notify_employee_mentioned` | Notify when an employee is tagged | `true` | Saved and shown only |
| `notify_unprocessed_message` | Notify about open messages not yet handled | `false` | Saved and shown only |

"Saved and shown only" means: the settings page (`dashboard/email/einstellungen`) loads and saves the value, but no server code and no other screen reads it. See problem 16 in `02.5-custom-shafts-problems.md`.

### Summary on the order

So that lists do not read every message, each send also writes onto the order (`custom_shafts`):

| Column | Written |
| --- | --- |
| `chat_last_at`, `chat_last_id`, `chat_last_message`, `chat_last_sender_role`, `chat_last_message_type` | On every new message |
| `chat_admin_unread` | +1 when the shop writes. Set to 0 when the admin marks the conversation read. |
| `chat_partner_unread` | +1 when FeetF1rst writes. Set to 0 when the shop marks it read. |

An order "has a conversation" when `chat_last_at` is filled.

## What happens when something is deleted

| Deleted | Effect on the chat |
| --- | --- |
| The order | Messages, files, and employee assignments stay, with an empty order link. No screen can reach them any more. |
| A message | Not possible through any address |
| The account that wrote a message | Every message of that account is deleted, with its tags. Its files and reaction stay with an empty message link. |
| An employee | Their messages, tags, and assignments stay, with an empty employee link |
| The partner | The settings row stays with an empty partner link |

## Functions

### Write a message (`sendMessage`)

Body:

| Field | Meaning |
| --- | --- |
| `message` | Text |
| `attachments` | List of `{ file_url, file_type }`. Entries without `file_url` are dropped. At most 30 are kept. |
| `reply_id` | The message being answered |
| `employee_id` (or `employeeId`) | Who in the shop is writing, see "Who is the sender" |
| `tag` | List of `{ id, name }` in the order the `@` names appear in the text. At most 20 are kept. |

Steps:

1. Work out `sender_role` and the employee as in the table above.
2. If there is no text and no file, answer `400` "Message or attachments required".
3. If `reply_id` is given and that message is not in this order, answer `400` "Reply message not found".
4. Save the message with its files and tags. `message_type` is `attachment` when there is a file, otherwise `normal`.
5. Write the summary onto the order and add 1 to the other side's unread count.
6. Answer `200` "Message sent successfully" with the message, its `reply` preview, and `tag` list.
7. After the answer, send the live update (see "Live updates").

Errors: an unknown order gives `404` "Order not found". An unknown tagged employee gives `404` "tag employee not found".

### Read a conversation (`getMessages`)

Query: `limit` (default 20), `cursor` (the id of the oldest message already shown). Newest messages come first. Each message carries sender, employee, files, reaction, tags, and a reply preview. `pagination.hasMore` says whether older messages exist. A wrong cursor gives `400` "Invalid cursor provided".

### Mark as read (`markAsRead`)

- Admin: every unread shop message (partner or employee) of this order becomes read, and `chat_admin_unread` becomes 0.
- Partner or employee: every unread FeetF1rst message of this order becomes read, and `chat_partner_unread` becomes 0.

Answer: `data.updatedCount`, how many messages changed. An unknown order gives `404`.

### Inbox list (`getConvercationList`)

Shows orders with a conversation, the latest one first.

| Logged in as | Which orders |
| --- | --- |
| Admin | All orders with a conversation |
| Partner | Own orders with a conversation |
| Partner with `employee_id` in the query | As that employee would see it. The employee must belong to this partner, otherwise `404` "Employee not found". |
| Employee | The shop's orders. If the shop has turned off `all_employees`, only orders given to this employee. |

Query values:

| Value | Meaning |
| --- | --- |
| `limit` | Default 20, at most 100 |
| `cursor` | Order id of the last row shown |
| `unread=true` | Only conversations with unread messages for this side |
| `search` | Words, all must match. Shop: order number, kind, customer name, other customer name. Admin also: partner name, email, business name. A leading `#` is ignored. |

Each row: order number, kind, customer, partner (email only for the admin), employees given the conversation, last message with its reaction, and this side's unread count.

### Start a new conversation (`searchNewConversation`)

Lists orders that have no message yet. Orders that are done (`Ausgeführt`), cancelled, neutral, or a draft are left out. The same "which orders" rules apply as in the inbox list.

Without a search, the newest orders come first (`limit` default 10, at most 100). With a search, each word must match somewhere, and results are ranked: exact match first, then "starts with", then "contains". Searched fields: order number, production number, other customer name and number, customer name, customer number, email, phone; the kind only when the word has 4 or more letters. The admin also searches partner name, email, phone, and business name.

The rows look like inbox rows with an empty last message and unread count 0. The conversation starts when the first message is sent.

### Total unread (`myTotalUnreadMessage`)

Admin: the sum of `chat_admin_unread` over all orders. Partner side: the sum of `chat_partner_unread` over the partner's own orders. Answer: `data.total`.

### Emoji reaction (`messageReaction`)

Body `reaction`, for example `"👍"`. An empty or missing value removes the reaction.

A partner may only react in their own orders (`403` "Not your order"). An unknown message gives `404` "Message not found". Reactions do not change unread counts or the order of the inbox. A live update `custom-shafts-reaction` goes to the open conversation (not to the person who reacted), to all admins, and to the partner.

### Give a conversation to employees (`addChatEmployees`, `removeChatEmployees`, `getChatEmployees`)

Body for add and remove: `custom_shafts_id`, and `employee_id` as one id, a list, or ids separated by commas.

- The order must belong to the shop of the logged-in partner or employee, otherwise `404` "Order not found". The admin may use any order.
- Add: only employees of the order's partner are added; others are skipped silently. If none is left, `400` "employee not found". Adding someone twice does nothing. Answer: `addedCount` and the employees.
- Remove: answer `deletedCount`.
- Get: query `custom_shafts_id`, `limit` (default 20, at most 100), `cursor` (employee id). Newest assignment first.

### Order header (`getContextInfo`)

Query `custom_shafts_id`. Returns order number, status, kind, the customer (name, number, email, phone), the other customer name and number, and the employees given the conversation. A partner or employee only gets their own shop's orders; otherwise `404` "Order not found".

### Settings (`setChatSettings`, `getChatSettings`, `getResetActivity`)

- Save: only the fields sent are changed. Yes/no fields count as "yes" only when the value is exactly `true`. `message_sending_type` must be `by_auth_token` or `by_user_id`, otherwise `400`. An empty `reset_activity` is saved as empty.
- Load: `404` "Chat settings not found" when the shop never saved them. The settings page then shows the defaults.
- `get_reset_activity`: the minutes, or `null` when not saved.

## Live updates

The server pushes chat events through Socket.IO (`socket/index.ts`).

Rooms:

| Room | Who joins |
| --- | --- |
| The account id | Every logged-in tab joins the room of its account id (`join`) |
| `admin-inbox` | Every admin tab |
| `custom-shafts-chat:<order id>` | A tab that has this conversation open (`custom-shafts-chat-room`, left with `leave-custom-shafts-chat-room`) |

When a message is sent:

| Receiver | Event | Extra |
| --- | --- | --- |
| Everyone in the open conversation's room, except the sender's account | `custom-shafts-message` | The message |
| Shop wrote: all admins | `custom-shafts-message` | Message, conversation row, admin unread count |
| FeetF1rst wrote: the partner's account room, and all admins | `custom-shafts-message` | Message, conversation row, that side's unread count |

No notification row and no push message is created for chat messages. The notification type `custom_shafts_chat` exists in the list but nothing writes it.

## Other places that count unread messages

| Where | How it counts |
| --- | --- |
| Partner balance list (`/v2/admin-order-transitions/get-all-transitions-tree`) | Per order: FeetF1rst messages not yet read |
| Partner header counter (unread counts handler in `module/v1/admin_order/treack/treack.controllers.ts`) | All FeetF1rst messages not yet read in the partner's orders |
| Admin order list (`/v3/admin-order/get-all-orders`) | `chat_admin_unread` per order |
| Admin count endpoint (`/v3/admin-order/calculation-info/*`) | Sum of `chat_admin_unread` |
| Clinical-care orders (`module/v4/clinical_assistant/orders`) | `chat_partner_unread` |

The first two count message rows, the rest read the counters on the order. Both are kept equal by "send" and "mark as read".

## A worked example

The shop "Orthopädie Weber" (partner `p1`) has order `cs1`, number `10023`, a shaft for customer Anna Schmidt. Employee Lena (`e7`) works on it.

1. Lena opens the inbox, picks herself on the "who is working" screen, and starts a new conversation. The screen calls `GET /search-new-conversation?search=10023` and shows order `10023`.
2. She uploads a photo; the screen puts it into S3 and gets `https://…/admin-order/chat/leather.jpg`.
3. The screen sends:

```json
POST /v3/admin-order/chat/send-message/cs1
{
  "message": "Is this leather colour still available?",
  "attachments": [{ "file_url": "https://…/admin-order/chat/leather.jpg", "file_type": "image/jpeg" }],
  "employee_id": "e7"
}
```

4. The database now has:

| Table | Row |
| --- | --- |
| `custom_shafts_chat` | `m1`: order `cs1`, `sender_id` `p1`, `employee_id` `e7`, `sender_role` `EMPLOYEE`, `message_type` `attachment`, `isRead` false |
| `custom_shafts_chat_attachment` | `a1`: message `m1`, the photo address, `image/jpeg` |
| `custom_shafts` `cs1` | `chat_last_id` `m1`, `chat_last_sender_role` `EMPLOYEE`, `chat_last_message_type` `attachment`, `chat_admin_unread` 1, `chat_partner_unread` 0 |

5. Every admin tab receives `custom-shafts-message` with `unread_count: 1`. The admin inbox shows order `10023` on top with a red 1.
6. The admin opens it. The screen calls `PATCH /mark-as-read/cs1`: `m1` becomes read and `chat_admin_unread` becomes 0.
7. The admin answers "Yes, in stock." That saves `m2` with `sender_role` `ADMIN` and sets `chat_partner_unread` to 1. The partner's account room receives the message, so Lena's inbox shows the red 1 until she opens the conversation.
