# Who may see a catalogue shoe

Some shoes in the menu are for every partner. Some shoes are reserved for a few partners. This chapter is that reservation.

The shoe itself — name, price, photo, leather — stays on the catalogue, described in `01-catalogue.md`. A partner's heart on a shoe is a private mark, described in `01.1-favourites.md`. A heart never moves a shoe in front of a reserved one.

## Names

| What a person says | What the system calls it |
| --- | --- |
| Reserved shoe, exclusive model | A catalogue shoe that has at least one row in `maßschaft_kollektion_reduse_access` |
| Public shoe | A catalogue shoe with no rows in that table |
| The badge on the card | **Exklusives Modell** |
| The flag on the shoe list | `isExclusive` |
| One reservation | One row: this shoe plus this partner |
| The shoe | `maßschaft_kollektion_id` |
| The partner | `partnerId`. A partner login and an employee login both carry this same partner id. The employee’s own id is `employeeId` and is not stored here. |
| Partner Dashboard | The catalogue at Custom shafts |
| Admin product screen | `feetf1rst-landing-page`, the product area where shoes are uploaded |

## The rule

| Reservations on this shoe | Who sees it in the partner menu |
| --- | --- |
| None | Everyone. The shoe is public. |
| One or more | Only the partners named on those reservations. |

An admin who is building the menu still sees every shoe. A partner sees the public shoes plus the shoes reserved for that partner.

Reserved shoes are listed first. After that, price decides the order. A filled heart does not change this order.

## The story, in order

1. Admin opens a shoe on the product screen and opens **access** for that shoe.
2. The screen searches partners who are not reserved yet, and the admin saves the ones they chose.
3. That shoe leaves the public menu. Each named partner sees it at the top of their catalogue, with the badge **Exklusives Modell**.
4. Every other partner’s menu leaves the shoe out. If they open it by its address, the answer is that the shoe was not found.
5. Admin can remove a partner from the reservation. When the last partner is removed, the shoe is public again.

The partner dashboard does not edit this list. It only shows the result: the shoe is hidden, or it is shown first with the exclusive badge.

## What is stored

One reservation is one row in `maßschaft_kollektion_reduse_access` (`prisma/admin-order.schma.prisma`).

| What a person means | Column | What is saved |
| --- | --- | --- |
| Identity of this reservation | `id` | A cuid. Nobody types it. |
| Which shoe | `maßschaft_kollektion_id` | The catalogue shoe’s `id`. |
| Which partner | `partnerId` | That partner’s user `id`. |
| When the reservation was made | `createdAt` | The time the row was inserted. |

The same partner cannot be reserved twice on the same shoe.

## What happens when something is deleted

| If this is deleted | What happens to the reservation |
| --- | --- |
| The catalogue shoe | Every reservation of that shoe is deleted with it. |
| The partner account | Every reservation of that partner is deleted with it. |

Removing one partner from a shoe deletes only that pair. The shoe stays in the catalogue.

## Who changes the list

Only an admin. The partner dashboard never calls these addresses.

The admin product screen talks to the catalogue API. The same work is available at `/custom_shafts/...` and `/v1/custom_shafts/...`. The code is in `module/v1/admin_order/custom_shafts.controllers.ts`. The screen’s calls are in `feetf1rst-landing-page/src/apis/productsCreate.js`.

| What the admin does | Where on the product screen | Request |
| --- | --- | --- |
| See who already has this shoe | Access panel for one shoe | `GET /custom_shafts/reduse-access/:shoeId` |
| Find partners who do not have it yet | Same panel, and the panel for many shoes at once | `GET /custom_shafts/search-partner/:shoeId` |
| Reserve the shoe for those partners | One shoe, or many shoes together | `POST /custom_shafts/reduse-access` |
| Take partners off one shoe | The panel for one shoe | `DELETE /custom_shafts/undo-reduse-access/:shoeId` |

Reserving sends the shoe ids and the partner ids together: `{ "ids": ["<shoe id>", ...], "partnerIds": ["<partner user id>", ...] }`. Every chosen shoe is paired with every chosen partner. A pair that already exists is skipped. The answer is `200`, “Access granted successfully”, and `grantedCount` is how many new reservations were written. `grantedCount` of `0` means every pair was already reserved. The many-shoes panel says that in the toast.

If the shoe list or the partner list is missing, the answer is `400`.

Partner search returns partner accounts who are not already reserved on this shoe. It can filter by name, business name, email, phone, or the partner’s own partner number. The “who already has it” list can filter by name, business name, or email. Both lists come back in pages of up to 100 names. The next page is asked by sending `cursor` as the last id from the previous page. `pagination.hasMore` says whether another page exists.

Removing partners sends `{ "partnerIds": ["<partner user id>", ...] }` to that shoe’s address. The answer is `200`, “Access revoked successfully”, and `revokedCount` is how many reservations were removed.

## What the partner sees

The catalogue at Custom shafts, and the same cards in the clinical shaft picker, load the shoe menu: `GET /custom_shafts/mabschaft_kollektion`.

For a partner and for an employee, the login’s `id` is the partner. The menu keeps a shoe when it is public, or when this partner is on its reservation list. Other reserved shoes are left out.

Each shoe reserved for this partner comes back with `isExclusive: true`. The product card shows **Exklusives Modell**, unless that shoe is the one currently selected. The selected badge wins.

Both screens then put reserved shoes first, and sort by price after that. The heart is not part of that order.

Opening one shoe uses the same rule. A partner who is not on the list, for a shoe that is reserved for others, gets `404` “Maßschaft Kollektion not found.” The message does not say the shoe is exclusive.

## A worked example

Shoe “City Boot” has no reservations. Every partner sees it. There is no exclusive badge.

1. Admin reserves it for Partner A and Partner B. Two rows are stored. `grantedCount` is `2`.
2. Partner A’s menu shows City Boot first, with **Exklusives Modell**. Partner B sees the same. Partner C’s menu no longer includes it.
3. Admin removes Partner B. One reservation remains. Only Partner A sees the shoe, still with the badge.
4. Admin removes Partner A. No reservations remain. City Boot is public again, and the badge is gone.
