# Favourite catalogue shoes (`maßschaft_kollektion_favorite`)

A favourite is a partner's private mark on a shoe in the menu. It does not change the shoe, the price, or any customer order. It only remembers "this partner wants this model easy to find again."

The table is `maßschaft_kollektion_favorite` in `prisma/admin-order.schma.prisma`. One row is one partner plus one catalogue shoe. The shoe itself stays in `maßschaft_kollektion`, described in `01-catalogue.md`.

## The story, in order

1. The partner opens the catalogue in the Partner Dashboard, on `dashboard/custom-shafts`. Each shoe card has a heart.
2. The list of shoes already says which hearts are filled. That yes/no is `isFavorite` on each shoe. It is not a column on the shoe. The list looks up this table for the shoes on the current page.
3. The partner clicks the heart. The card turns red immediately.
4. The screen calls `POST /favorite_models/favorite` with that shoe's `id`.
5. If this partner had no row for that shoe, one row is created and the answer says the shoe is now a favourite. If a row was already there, that row is deleted and the answer says it was removed.
6. If the save fails, the heart goes back to how it was, and the partner sees "Favorit konnte nicht gespeichert werden."

The same heart in the clinical shaft picker calls the same address.

A second address, `GET /favorite_models/get-all-favorites`, returns every shoe id this partner has marked, newest first. The catalogue screen does not call it. The hearts on the cards come from the shoe list.

## What is stored

| What it means | Column | What is saved |
| --- | --- | --- |
| Identity of this mark | `id` | Text. The toggle writes a random UUID. Other tables use a cuid. Both are plain text, so the row still works. |
| Which shoe | `maßschaft_kollektion_id` | The catalogue shoe `id`. Required. The shoe must exist. |
| Which partner | `partnerId` | The token's `id`. That value is the partner's user id. An employee token still carries the partner in `id`, and puts the employee on `employeeId`. This table does not store `employeeId`. |
| When they marked it | `createdAt` | The time of the insert. Removing and marking again writes a new time. |

One partner can mark many shoes. One shoe can be marked by many partners. The same partner cannot mark the same shoe twice. The database rule is unique on `partnerId` together with `maßschaft_kollektion_id`.

## What happens when something is deleted

| If this is deleted | What happens to the favourite |
| --- | --- |
| The catalogue shoe | Every favourite of that shoe is deleted with it. |
| The partner account | Every favourite of that partner is deleted with it. |

Un-marking the heart deletes only that one row. The shoe stays in the menu.

## Who the heart belongs to

The save reads `id` from the JWT and stores that as `partnerId`.

A partner token has `id` set to that partner. An employee token has the same `id` (the partner) and a separate `employeeId`. The favourite row, the filled heart, and the answer are the same in both cases, because both tokens point at one partner. `employeeId` is not written here.

## The two addresses

Both exist as `/favorite_models/...` and `/v1/favorite_models/...`. Same code. Mounted in `module/v1/index.ts`. Handler file: `module/v1/admin_order/favorite_models/favorite_models.controllers.ts`.

### Mark or un-mark

`POST /favorite_models/favorite`  
The handler stores the token's `id`, which is the partner for a partner and for an employee.  
Body: `{ "modelId": "<catalogue shoe id>" }`

`modelId` is the shoe's `id`, the same id used everywhere else. Missing or blank `modelId` answers `400`, "modelId is required."

The save is one database statement, so a single click cannot end halfway:

1. Delete the row for this partner and this shoe, if it exists.
2. If nothing was deleted, and the shoe exists, insert one row.
3. Answer from what happened.

| Result | Answer |
| --- | --- |
| Shoe does not exist | `404`, "Model not found." Nothing is inserted. |
| Row was inserted | `200`, message "Model added to favorites", `data.isFavorite` is `true`, `data.modelId` is the shoe id. |
| Row was deleted | `200`, message "Model removed from favorites", `data.isFavorite` is `false`. |
| Database error | `500`, "Failed to update favorite." |

The screen does not send "please add" or "please remove." One click always flips. The card guesses the new state, then replaces that guess with `data.isFavorite` from the answer.

### List this partner's marks

`GET /favorite_models/get-all-favorites`  
No query parameters. The list is the hearts of the partner in the token's `id`.

`200` returns only the shoe id and the time, newest first. It does not return the shoe name, photo, or price.

```json
{
  "success": true,
  "message": "All favorites fetched successfully",
  "data": [
    { "modelId": "<shoe id>", "createdAt": "2026-10-09T00:00:00.000Z" }
  ]
}
```

To show a card, the screen still has to load the shoe. That is why the catalogue uses the shoe list, which already attaches `isFavorite` to each shoe the partner is allowed to see.

## Where the partner dashboard calls the API

In the Partner Dashboard, every call below goes out through `lib/axiosClient.ts`. The base address is `NEXT_PUBLIC_API_ENDPOINT`. The login token in `localStorage` is attached by that client.

### The shoe list, which paints the heart

| | |
| --- | --- |
| Screen | Catalogue at `dashboard/custom-shafts`, and the same cards inside the clinical shaft picker |
| Hook | `hooks/customShafts/useCustomShafts.ts` |
| Client function | `getAllCustomShafts` in `apis/customShaftsApis.ts` |
| Request | `GET /custom_shafts/mabschaft_kollektion` |
| Query | `page`, `limit`, `search`, `category`, `sortPrice`, and `gender` when a gender is selected |

The hook copies `isFavorite` from each shoe onto the card. A missing flag stays empty, so the heart is not filled.

### The heart click, which saves the mark

| | |
| --- | --- |
| Button | `components/CustomShafts/CustomShaftProductCard.tsx`. The heart sits on the top right of the card. While the save runs, the heart is replaced by a spinner and the button does not accept another click. |
| Catalogue page | `app/(dashboard)/dashboard/custom-shafts/page.tsx`, function `handleToggleFavorite` |
| Clinical picker | `components/clinical/ClinicalSchaftChoiceModal.tsx`, the `onToggleFavorite` passed into the same card |
| Client function | `toggleFavoriteModel` in `apis/customShaftsApis.ts` |
| Request | `POST /favorite_models/favorite` with body `{ modelId: "<shoe id>" }` |

Both screens do the same three steps. They paint the new heart immediately, they wait for `data.isFavorite` from the answer, and if the request fails they put the heart back and show "Favorit konnte nicht gespeichert werden."

`GET /favorite_models/get-all-favorites` is not called anywhere in the partner dashboard. The hearts on the cards come only from the shoe list.

## How the shoe list paints the heart

`GET /custom_shafts/mabschaft_kollektion` loads a page of shoes, then asks this table: "which of these ids does this partner have?" Those ids come back as `isFavorite: true`. The others are `isFavorite: false`.

The partner id for that check is the token's `id`. For an employee that is still the partner id, so the hearts on the page are that partner's hearts.

The heart does not change the order of the menu. Exclusive shoes always come first. After that, price decides the order. A filled heart is only the colour of the icon.

## A worked click

The partner has no row for shoe `cmShoe1`.

1. They click the heart. The card turns red.
2. `POST /favorite_models/favorite` with `{ "modelId": "cmShoe1" }`.
3. One new row: their `partnerId`, `maßschaft_kollektion_id` = `cmShoe1`, a new `createdAt`.
4. The answer has `isFavorite: true`. The heart stays red.
5. They click again. The same request deletes that row. The answer has `isFavorite: false`. The heart is empty.
6. If the second click fails, the card puts the heart back to red and shows the German error toast.
